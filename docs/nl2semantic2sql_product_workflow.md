# GIS Data Agent 智能问数产品流程与治理边界

**版本**：v1.0

**日期**：2026-08-25
**适用范围**：数据源接入、统一元数据、本体模型、语义层、左侧对话框智能问数及结果可视化。

## 1. 正式产品流程

所有新数据源都遵循同一条链路：

```text
数据源接入
  -> 虚拟入湖 / 物理入湖
  -> 全局统一元数据目录
  -> 技术本体候选与领域本体映射
  -> 专家本体审核发布
  -> 语义层配置与审核发布
  -> 左侧对话框智能问数
  -> 结构化结果、图表和地图交互
```

Benchmark 是这条链路的验证和发布门，不是用户日常操作入口。

## 2. 数据源接入

### 2.1 虚拟入湖

虚拟入湖登记连接、权限、数据库/schema、刷新策略和治理指纹，发现阶段只保存技术元数据快照，不复制业务数据行。查询阶段在源库只读下推，并受 source registration、schema allowlist 和执行门禁控制。

Liveability 和 Makani 当前采用 `registered_governed_virtual_read_only`。这两个库的元数据发现已经覆盖 `public` schema 中的全部登记资源。

### 2.2 物理入湖

物理入湖执行采集或同步，将数据写入湖仓或受治理存储，并登记存储位置、快照/分区、版本、刷新状态和血缘。物理入湖与虚拟入湖必须共用数据源注册、元数据合同和下游本体/语义引用方式。

当前物理入湖已有独立管道和资产目录能力，但“新数据源接入时统一选择虚拟或物理模式”的完整向导仍是产品化待办。

## 3. 全局统一元数据

无论 ingestion mode 为 `virtual_source` 还是 `physical_lake`，数据源成功接入后都必须进入统一元数据目录。目录的最小合同包括：

- 数据源、连接标识、数据库和 schema；
- 表、视图、资源类型及稳定资源 ID；
- 字段、类型、可空性、默认值和注释；
- 主键、外键、索引及约束证据；
- 空间字段、坐标系、几何类型和空间范围；
- 行数估计或物理快照统计；
- ingestion mode、源行是否持久化、血缘和刷新状态；
- discovery/profile fingerprint 和 metadata version。

用户查看路径是：

`数据资源 -> 元数据 -> 资源目录 -> 点击表 -> 查看字段`

原始 JSON 只能作为审查详情或导出格式，不能作为默认用户界面。

当前统一目录 API 为 `/api/metadata/unified`，支持虚拟和物理资产；资源目录支持表级点击和字段展开。

## 4. 本体模型

本体由三类事实组成，不把原始表名直接当作业务本体：

1. **技术本体候选**：由元数据反向生成技术实体、属性、主外键关系、空间特征和来源映射。
2. **领域基础本体**：由领域标准和专家治理定义，例如 Abu Dhabi DMT 城市与市政本体。
3. **数据源 overlay**：将某个数据库的表和字段映射到领域概念，并记录证据、版本、置信度和审核状态。

自动生成使用元数据、数据字典、约束信息和可选的受控 profiling 证据；自动生成结果属于 `candidate`，不能直接授予生产 Join 或业务指标权限。

专家治理必须支持草稿、修改、校验、审核和发布，至少覆盖：概念定义、别名、多语言标签、领域归属、属性、关系、映射、生命周期和运行时准入。

Liveability 与 Makani 应作为同一个 Abu Dhabi DMT 本体下的两个 overlay，而不是两个独立本体。唯一权威查看和治理入口是：

`模型 -> 本体模型`

“阿布扎比问数验证”不属于产品导航；问数动作统一走左侧对话框。

当前已具备 DMT 基础本体包、两个业务库的技术 overlay 产物及本体草稿 API；overlay 在统一本体工作台中的逐库逐表逐字段展示仍需继续完善。

## 5. 语义层管理

语义层建立在元数据和本体之上，负责问数可执行语义：

- 业务资产、业务名称、别名和多语言术语；
- 本体概念 ID、元数据资源 ID 和字段绑定；
- 粒度、字段业务角色、空间使用方式；
- 指标合同、公式、值域和能力；
- 关系候选、基数、Join 准入和跨源边界；
- 查询策略、澄清规则、拒答规则和敏感性约束。

语义层不得复制或绕过本体审核。配置必须经过：

`草稿 -> 校验 -> 审核 -> 发布`

只有发布版本才能进入问数运行时。语义 CRUD 与 immutable ontology package 不是自动双向写入关系；从语义候选进入本体草稿必须走受治理的显式流程。

## 6. 左侧对话框智能问数

用户只在左侧对话框提问。运行时依次执行：

1. 识别问题范围和数据源；
2. 从已发布本体和语义层召回候选；
3. 检查资产、字段、粒度、关系和能力；
4. 对歧义问题澄清，对未审核或越权问题拒答；
5. 默认使用 `baseline_sql` 生产路线；
6. `semantic_ir_experimental` 仅作为受限候选路线；
7. 通过执行门禁后生成只读查询并执行；
8. 返回结果、来源、语义计划、门禁决策和可视化合同。

Benchmark Gold SQL、Gold result 和业务源数据行不得进入运行时 prompt 或普通证据 API。

## 7. 结果可视化与地图交互

问数结果使用结构化 presentation contract，而不是让模型直接生成任意前端代码。合同至少支持：

- 表格、KPI、柱状图、折线图、饼图和分组比较；
- 时间序列、空间统计和结果排序；
- 地图图层、空间筛选、对象点击、明细钻取和回到对话上下文。

空间结果必须声明 geometry、空间对象类型、坐标系、图层来源和可交互字段。地图交互通过受治理的 workspace update 或地图图层发布协议完成，并保留查询和来源证据。

当前左侧聊天已经具备问数执行、结果展示和地图更新链路；通用全库可视化合同和更多空间交互类型仍需扩展。

## 8. 当前完成度与待办

### 已完成或可用

- Liveability、Makani 虚拟来源登记和 metadata-only discovery；
- 统一元数据 API、表级资源目录和字段展开；
- Abu Dhabi DMT 基础本体包及两个数据源技术 overlay；
- 统一本体工作台、草稿/校验/发布接口；
- 语义层配置、CRUD、版本门禁和已审核资产运行时；
- 左侧对话框问数、baseline 默认路线和受限 SemanticQueryIR 路线；
- 结果表格、问数证据和部分地图联动；
- v1/v2/v3 benchmark 及双路线比较报告。

### 后续必须继续推进

1. 将虚拟/物理模式收敛到统一数据源接入向导，并让新数据源动态进入元数据目录；
2. 将 Liveability/Makani overlay 接入唯一“本体模型”工作台，支持按数据源、表、字段、概念和审核状态检索；
3. 建立“元数据候选 -> 本体草稿 -> 专家审核 -> 发布”的产品流程；
4. 将语义层配置与本体版本、metadata fingerprint 和 source overlay 版本显式绑定；
5. 扩充 benchmark 的困难题、全库选表、跨表关系、空间问数、拒答和多语言覆盖；
6. 根据失败分类提升候选召回、字段角色识别、粒度判断、澄清策略和结果可视化；
7. 在没有全库、独立 holdout 和真实结果合同证据前，不宣称“全库任意问数”或“100% 准确率”。

## 9. 2026-08-25 当前对齐与继续推进记录

本记录是当前产品口径的持久化依据，后续实现和验收均以此为准：

1. 数据源接入先选择虚拟入湖或物理入湖；当前 Liveability、Makani 保持虚拟入湖，源库只读下推，不把源数据行复制到运行时。
2. 两种入湖模式都进入同一个全局元数据目录。元数据默认以资源目录、表详情和字段详情呈现，JSON 只作为审查或导出格式。
3. 本体由“元数据反向生成的技术候选 + 领域基础本体 + 数据源 overlay”组成。自动生成结果必须是候选；专家可以在本体草稿中修改、校验、送审和发布。
4. Liveability、Makani 是 Abu Dhabi DMT 统一本体下的数据源 overlay，不新增第二套本体入口；唯一权威入口是“模型 -> 本体模型”。
5. 语义层绑定已发布本体、元数据指纹和 overlay 版本，负责业务资产、字段角色、粒度、指标和 Join 准入；未发布配置不能进入运行时。
6. 智能问数只从左侧对话框进入。`baseline_sql` 仍是默认生产路线，`semantic_ir_experimental` 只能作为受限候选路线；“阿布扎比问数验证”不属于产品导航。
7. Benchmark 的 100% 选择覆盖只代表候选选择或策略门禁通过，不代表 SQL、执行结果、空间结果或可视化正确率。本轮继续增加独立 holdout、长尾选表、粒度/空间/关系/拒答题，并分层记录执行与结果等价率。

### 本轮继续推进的交付边界

- 将数据源 overlay 接入统一本体工作台，按数据源、表、字段、概念和审核状态查看，而不是在页面中写死两个库。
- 给 overlay 读模型绑定 source registration、metadata/profile fingerprint、semantic version 和 base ontology version，发现漂移时显示为待复核。
- 保持 ontology immutable package 与语义 CRUD 分离；需要进入本体的变更必须显式创建 ontology draft。
- 运行可复现的 benchmark 评测，并将失败分类为模型生成、候选召回、语义准入、SQL 执行、结果等价、安全门和展示/地图问题。

### 当前不能宣称的结论

当前证据不足以宣称“全库任意问数已完成”或“端到端 100% 准确率”。可以宣称的是：已具备受治理的虚拟入湖、统一元数据、本体候选/审核链路、语义层门禁、左侧问数入口，以及一组受控 benchmark 的可复现基线；端到端全库能力仍按上述交付边界推进。

### 2026-08-25 评测记录

本地使用当前候选选择器重新执行了公开 benchmark 的第一阶段评测：

- Benchmark v2：18 个可执行资产选择题，单资产 Top-1 为 `1.0`；3 个多资产题的审核资产集覆盖为 `1.0`；非执行安全门为 `1.0`；总体选择层通过率为 `1.0`。
- Benchmark v3：12 个可执行题，单资产 Top-1 为 `1.0`；7 个复合资产题的审核资产集覆盖为 `1.0`；10 个非执行题的安全门为 `1.0`；总体选择层通过率为 `1.0`。
- 这些报告的 `claim_boundary` 明确标记 SQL 正确性、结果正确性和运行时 LLM 质量未评估。历史受控真实源 v6 报告的 36/36 通过仍作为已发布基线，不因本次选择器改动自动改写。

本次选择器修正是通用规则：识别“按多个维度分组的单一业务对象”，避免把行政区等分组容器误升格为 Join 资产；只有至少两个非分组业务对象才触发复合资产关系检查。该规则由候选目录和语义字段角色驱动，没有添加题目 ID 或物理表名特判。
