# TWM 自然资源部原型演示脚本

版本日期：2026-07-03（自然资源部现场演示前复核版）
演示入口：`http://127.0.0.1:8000/`
主演示数据包：`twm_bishan_multi_admin_eval`（璧山多行政单元评估样例）
主业务场景：璧山国土空间审查样例
数据边界：演示/非生产数据，不能作为权威审批结论。

## 演示目标

用同一条璧山国土空间审查数据主线，说明 TWM 如何把数据基础、地图定位、状态构建、规则审查、风险推演、方案比选和数据边界串成一条可复核的业务链路。

本脚本用于人工操作验证。每一步都给出“操作”“预期看到”“讲解要点”。如果某一步预期不一致，应停止演示并记录问题。

## 0. 先统一现场口径

这一版演示只用一条主线：

1. 数据证据和地图浏览主线使用 `璧山多行政单元评估样例`，数据包 ID 为 `twm_bishan_multi_admin_eval`。
2. 操作推演也选择 `璧山多行政单元` 预设，不再用 `璧山演示` 作为主流程。
3. `一张图村庄规划标准样例` 只作为可选旁路，用来说明系统会识别坐标转换问题；不要把它混入主业务故事。
4. 现场所有结论都要加上“演示样例数据下”的限定，不能说成自然资源部真实权威数据已经验证通过。

建议现场少用内部术语，按下面方式解释：

| 界面/内部词 | 现场说法 |
| --- | --- |
| TWM 状态 | 一次可计算的业务快照，也可以理解为把这批数据整理成一个可复核的台账版本 |
| 构建状态 | 把原始图层和表格整理成对象、关系和业务记录，后续检查都基于这个版本做 |
| 规则命中 | 哪个项目、图斑或边界触碰了哪条审查规则 |
| 证据审计 | 说明每个判断用了哪些数据，哪些够说明问题，哪些还需要人工复核 |
| 验证口径 | 说明当前结果最多能说到什么程度，哪些结论还不能对外承诺 |
| 技术载荷 | 系统真实返回的结构化数据，主要给技术人员核查 |

## 1. 数据流总览：数据是怎么一步步变化的

演示时建议先讲这张“数据流”，让领导知道每一步不是换一套数据，而是同一批数据被逐步加工。

| 步骤 | 输入是什么 | 系统做了什么 | 输出变成什么 |
| --- | --- | --- | --- |
| 数据基础浏览 | `twm_bishan_multi_admin_eval` 中的 GeoJSON 图层、CSV 表格、影像索引和说明文件 | 检查文件清单、字段、样例属性、坐标是否能叠加 | 可上图的数据目录和数据质量提示 |
| 地图联动 | 项目、图斑、永久基本农田、生态红线、规划分区等空间图层 | 按坐标和图层类型叠加到地图 | 审查范围、项目位置和管控边界的空间视图 |
| 构建状态 | 同一批空间图层和业务表格 | 把每条要素或记录变成业务对象，把空间相交、隶属、审批、复核、证据关系变成关系 | 一个带版本号的 TWM 状态，也就是可计算业务快照 |
| 规则审查 | TWM 状态 | 按规则检查项目和边界、图斑、规划分区之间的冲突 | 规则命中、风险解释、证据项、需要复核的对象 |
| 风险预测/验证/审计 | 当前状态、规则命中、候选动作和证据 | 推演风险和收益，判断数据是否足以支撑结论，列出证据来源 | 风险预测结果、验证阶段、证据审计清单 |
| 方案比选 | 当前状态、候选方案、硬约束和风险结果 | 过滤不可行方案，比较收益、风险和可解释性 | 推荐方案、阻断方案和地图联动图层 |
| 回到数据证据 | 全流程结果和原始数据清单 | 说明哪些结论已有演示数据支撑，哪些必须等真实权威数据 | 能力边界、基线对比、下一步数据需求 |

一句话概括：

> 原始数据进来时是“文件和表”；构建状态后变成“对象、关系和业务记录”；规则和方案跑完后变成“风险、证据、复核任务和推荐方案”；最后再回到数据证据页说明这些结论能说到什么程度。

## 2. 演示前准备

操作：
1. 打开 `http://127.0.0.1:8000/`。
2. 登录后进入右侧 `智能分析`。
3. 打开 `TWM`。

预期看到：
- 页面标题为 `国土空间世界模型（TWM）`。
- 子 tab 包含 `总览地图`、`数据证据`、`操作推演`、`技术载荷`。
- 默认处在 `总览地图`。

讲解要点：
> 这不是一个孤立地图插件，而是 GIS Data Agent 中面向国土空间审查的世界模型原型。今天只沿着璧山多行政单元评估样例走一遍，重点看数据怎么从原始图层变成可检查、可解释、可复核的业务过程。

## 3. 数据证据：先确认数据基础是什么

操作：
1. 切换到 `数据证据`。
2. 在 `数据基础浏览器` 中确认选中 `璧山多行政单元评估样例`。
3. 如果没有选中，点击 `浏览 璧山多行政单元评估样例`。
4. 在 `空间图层目录` 中找到 `synthetic_projects.geojson`，点击该行 `上图`。
5. 再点击 `全量加载空间数据`。
6. 在 `坐标诊断` 的图层列表中，点击 `parcel_current.geojson` 的 `隐藏`，再点击 `显示`。

预期看到：
- 数据包 ID 显示 `twm_bishan_multi_admin_eval`。
- 总量显示 `22,401`。
- 面板中出现 `空间图层目录`，至少能看到 `parcel_current.geojson`、项目、永久基本农田、生态红线、规划分区、年度变化等空间图层。
- 每个空间图层行能看到字段数量、代表性字段和样例属性；项目图层中应能看到 `XMMC`、`YDMJ`、`approval_status` 等字段。
- 点击 `synthetic_projects.geojson` 的 `上图` 后，面板出现 `已联动图层 synthetic_projects.geojson，90 个空间要素`，地图先显示项目空间图层。
- 面板中出现 `已全量联动 6 个空间图层、21,603 个空间要素`。
- 面板中出现 `坐标诊断`，主演示包状态为 `可直接叠加`。
- `坐标诊断` 图层列表中出现 `隐藏/显示` 开关；隐藏 `parcel_current.geojson` 后，地图应从 6 个图层变成 5 个图层，重新显示后恢复 6 个图层。
- 中间地图出现密集图斑、项目、管控边界等空间图层。
- 当前数据性质仍显示为 `演示/非生产`。

人工核查重点：
- 这一步不是采样预览，而是全量加载当前主演示数据包的 GeoJSON 空间要素。
- 在全量加载前，先看 `空间图层目录`，并用字段/样例属性说明每个图层不只是几何轮廓，还带有审查所需的业务属性。
- 全量加载后，用图层开关临时隐藏大图斑层，再恢复显示，说明演示地图不是静态图片，而是可以按图层聚焦查看。
- 看到的空间范围应与后续 `总览地图 -> 定位审查区` 保持同域，不应跳到另一个区域。
- 如果坐标诊断显示 `需 CRS 转换`，不能继续把该数据包作为当前地图叠加演示对象。

讲解要点：
> 先把数据基础讲清楚。当前主演示数据包是璧山多行政单元评估样例，包含空间图斑、项目、永久基本农田、生态红线、规划分区、年度变化以及规则、审批、复核、证据索引等表格。空间图层目录里能看到字段和样例属性，例如项目名称、用地面积、审批状态、风险场景等；这说明 TWM 消费的是带业务语义的空间对象，不是几张静态图。它能支撑端到端原型演示，但仍不是自然资源部门权威生产数据。

可选旁路，不纳入主流程：
> 如果需要说明系统能识别坐标问题，可以临时浏览 `一张图村庄规划标准样例`，看到 `需 CRS 转换` 后马上切回 `璧山多行政单元评估样例`。这只是数据体检能力展示，不是今天的主线数据。

## 4. 总览地图：确认空间范围和数据基础对应

操作：
1. 切换到 `总览地图`。
2. 点击 `定位审查区`。

预期看到：
- 地图状态显示 `已联动：审查区定位`。
- 中间地图显示审查范围、拟建项目、硬约束边界。
- 该空间位置应与刚才 `全量加载空间数据` 看到的璧山多行政单元范围一致。

人工核查重点：
- 如果定位审查区和全量数据图层明显不在同一区域，说明演示不能继续。
- 当前脚本要求二者对应到 `twm_bishan_multi_admin_eval` 的空间范围。

讲解要点：
> 领导看惯了地图，所以我们从地图入口开始讲业务对象。这里看到的审查范围、项目、图斑和管控边界，都要和刚才的数据目录对应起来。也就是说，地图不是单独画出来的展示图，而是同一批数据的空间视图。

这一页要讲清楚的价值：
- 数据范围一致：数据目录和地图定位指向同一个审查范围。
- 地图可复核：项目、图斑和管控边界可以按图层查看，不是静态截图。

## 5. 操作推演：构建可计算业务快照

操作：
1. 切换到 `操作推演`。
2. 点击 `璧山多行政单元`。
3. 在 `项目名` 中填写一个演示项目名，例如 `TWM 自然资源部演示`。
4. 点击 `创建项目`。
5. 点击 `构建状态`。

预期看到：
- 项目创建成功。
- `选择项目` 中出现刚创建的项目名。
- 状态摘要出现对象数和关系数。
- 对象数和关系数应大于 100；当前 Docker 验证环境实测约为 `22,531` 个对象、`43,329` 条关系，现场以界面实际显示为准。
- 多行政单元数据量较大，`构建状态` 可能需要约 1-2 分钟；点击后等待状态摘要出现，不要重复点击。

这里必须讲清楚“状态”是什么：

> TWM 状态不是“页面状态”，也不是某个按钮状态。它是一份带版本号的业务快照：系统把这批数据中的项目、图斑、边界、规划分区、年度变化、审批记录、复核任务、规则记录、遥感/文档证据索引整理到同一个台账版本里。后面的规则检查、风险预测、证据审计和方案比选都基于这个版本做，所以结果可以追溯到同一批输入数据。

状态里通常包括三类内容：

| 类型 | 内容示例 | 作用 |
| --- | --- | --- |
| 业务对象 | 行政单元、地块图斑、建设项目、永久基本农田、生态红线、规划分区、城镇开发边界、年度变化斑块、审批记录、复核任务、规则评价记录、证据索引 | 说明“审查对象有哪些” |
| 对象关系 | 项目属于哪个行政单元、项目覆盖哪些图斑、项目是否与永久基本农田/生态红线/规划分区相交、年度变化斑块关联哪些地块、证据材料对应哪个项目或规则 | 说明“对象之间是什么关系” |
| 版本和质量信息 | 数据来源、坐标状态、构建时间、对象数、关系数、是否合成/非生产、缺哪些真实生产历史 | 说明“这个状态能不能用于强结论” |

数据在这一步发生的变化：

1. `parcel_current.geojson` 这类图层从“空间要素集合”变成“地块对象集合”。
2. `synthetic_projects.geojson` 这类图层从“项目图斑”变成“可审查项目对象”。
3. 空间相交、包含、邻接等计算结果变成“项目和地块/红线/规划分区之间的关系”。
4. `approval_records.csv`、`review_tasks.csv`、`rule_evaluation.csv` 等表格从“行记录”变成“审批、复核、规则评价等业务记录”。
5. 证据索引从“文件清单”变成“某个判断可以引用的证据项”。

讲解要点：
> 这一步相当于把同一批原始图层和表格整理成一个可计算的业务台账。以前人工审查时，人员需要在多个图层、多个表、多个材料之间来回找关系；TWM 的价值是把这些对象和关系先整理清楚，再让后续规则、预测、方案和审计都使用同一个台账版本。

## 6. 规则审查：从空间叠加变成可解释风险

操作：
1. 在 `操作推演` 中点击 `检查业务规则`。
2. 切换到 `总览地图`。

预期看到：
- 地图状态显示 `已联动：风险命中`。
- 地图上出现红色风险命中区域。
- 右侧或操作区中规则命中数量大于 0，证据数量大于 0；当前 Docker 验证环境实测约为 `140` 条规则命中、`556` 个证据项，现场以界面实际显示为准。
- 多行政单元规则审查可能需要约 1 分钟；点击后等待风险命中结果出现，不要重复点击。

人工核查重点：
- 红色风险区域应仍在主演示数据包空间范围内。
- 不应只看到状态文字变化，而地图没有变化。

讲解要点：
> 传统 GIS 可以做叠加，但 TWM 不只回答“有没有相交”。它还会说明哪个项目、哪块地、哪条管控边界、哪条规则发生了关系，并把这个关系组织成风险和证据。这样后面才能继续做复核、预测和方案比选。

这一页要讲清楚的价值：
- 把空间叠加结果变成业务风险清单。
- 风险结果能回到地图，不脱离原始空间位置。
- 每条风险后面要能追溯到规则和证据，而不是只有红色图斑。

## 7. 风险预测、验证和审计：说明结论能说到什么程度

操作：
1. 切回 `操作推演`。
2. 点击 `风险预测`。
3. 点击 `验证口径`。
4. 点击 `证据审计`。

预期看到：
- `风险预测` 后结果区出现规划收益、约束风险、可信度等信息。
- `验证口径` 后出现阶段列表或验证结论。
- `证据审计` 后证据项数量大于 0。

讲解要点：
> 这里不要说“系统已经给出生产结论”。正确说法是：系统基于当前演示状态推演风险、收益和不确定性，并检查这些结论有没有足够数据支撑。如果数据还不够，系统会把结论降级为“需要人工复核”或“只能作为原型验证”，不会包装成权威审批结论。

数据在这一步发生的变化：

1. 当前状态和规则命中进入预测模块，输出风险、收益、可信度等指标。
2. 验证口径把结果分层：哪些只是工程链路验证，哪些可以做业务复核辅助，哪些还不能作为生产结论。
3. 证据审计把每个判断关联到证据项，说明用了哪些图层、表格、规则记录或材料索引。

如果被问“模拟器到底做了什么”，按下面口径回答：

> 这里的模拟器不是生成一张未来地图，也不是替代审批人员下结论。它做的是：基于当前这份 TWM 状态、已经命中的规则、证据是否完整和我们选择的治理动作，推演这个动作下的风险、收益和可信度。它把“现在有什么对象和冲突”变成“如果采取这个动作，触碰管控边界的风险大概会上升还是下降、方案可能带来多少业务收益、这个判断有多可信、还缺什么证据”。

模拟器实际走五步：

1. 读取当前状态：对象数、关系数、图斑/项目/边界/审批/复核/证据索引，以及规则命中结果。
2. 读取当前动作：例如 `保护`、目标角色 `项目`、当前业务场景、证据是否完整，以及系统自动生成的合规性检查。
3. 先做动作可行性检查：如果动作触碰永久基本农田、生态红线、用途管制等硬约束，或者证据不足，就把这个动作标成阻断或需要复核。
4. 计算三类结果：约束风险、规划收益、可信度。约束风险受高风险规则命中、数据质量、非生产数据、证据完整程度和硬约束阻断影响；规划收益受动作类型、业务场景、风险压力和证据情况影响；可信度受证据完整程度、不确定性和是否缺少真实历史审批结果校准影响。
5. 生成一个“未来状态摘要”：不是逐宗地预测每个边界点，而是给出未来对象/关系规模、风险压力、收益变化、动作约束和证据缺口，供验证和方案比选继续使用。

现场可以这样举例：

> 比如同样是一个建设项目，如果已经命中了生态红线或永久基本农田规则，模拟器不会只看项目收益，而会把约束风险抬高；如果证据覆盖不足，它不会给强结论，而是把可信度压低并要求人工复核。这样它输出的是“可解释的风险-收益-证据判断”，不是一句黑箱预测。

`验证口径` 进一步做的事：

1. 重新跑一次预测，确认当前状态能不能支持未来状态判断。
2. 做一个简化的对照推演：不采取动作和采取动作分别推几期，看风险、收益、可信度的变化方向。
3. 按阶段列出结论：状态构建、未来预测、约束预测、对照推演、规划收益、能否在现有地图和数据链路中跑通。
4. 如果某一阶段证据不足、规则未通过或生产数据缺失，就把最终结论降级为“需要人工复核”（技术载荷中可能显示为 `review`），也就是只能作为复核辅助。

`证据审计` 进一步做的事：

1. 统计规则命中、复核任务和证据项数量。
2. 检查证据项是否有可追溯标识。
3. 汇总风险严重程度，说明哪些判断背后有数据，哪些还缺证据。
4. 这个结果用于向领导说明“系统为什么这么判断”，也用于防止演示数据被误说成生产结论。

这一页要讲清楚的价值：
- 系统不仅给结果，还说明结果的支撑程度。
- 对外能说清楚的就说清楚，不能说清楚的明确标成需要真实数据或人工复核。
- 这能避免原型演示把合成数据、公开样例或工程测试误说成生产验收。

## 8. 方案比选：从候选方案中选出可解释建议

操作：
1. 在 `操作推演` 中点击 `载入候选`。
2. 点击 `方案比选`。
3. 切换到 `总览地图`。

预期看到：
- 候选方案数量大于 0。
- `方案比选` 后出现推荐方案。
- 地图状态显示 `已联动：推荐方案`。
- 地图上出现推荐方案和阻断/风险方案图层。

人工核查重点：
- 推荐方案和阻断方案应仍在主演示数据包空间范围内。
- 如果方案结果没有地图联动，不适合领导演示。

讲解要点：
> 这里不要只说“模型自动推荐”。正确说法是：系统从候选方案中排除触碰硬约束或风险过高的方案，再比较收益、风险和证据支撑情况，给出一个可以解释、可以回到地图核查的推荐结果。推荐方案不是替代人工审批，而是帮助审查人员更快定位可行方向和风险来源。

数据在这一步发生的变化：

1. 候选方案进入当前 TWM 状态。
2. 系统把候选方案和硬约束、风险命中、收益指标做关联。
3. 输出推荐方案、被阻断方案、风险较高方案，以及选择理由。
4. 推荐结果回到地图，便于现场核查空间位置。

如果被问“规划器到底做了什么”，按下面口径回答：

> 这里的规划器不是凭空自动画出一个最终审批方案，也不是自动审批。它更准确的角色是“候选方案的审查器和排序器”。它先读取候选方案包，再逐个检查哪些方案触碰硬约束、哪些需要复核、哪些证据不足，然后用同一套模拟器给每个候选方案算风险、收益和可信度，最后只从合法可行的候选方案里选推荐方案。

规划器实际走六步：

1. 读取候选方案包：当前演示使用 `data_agent/test_data/twm_bishan_multi_admin_eval/optimization`，里面包括候选方案、可行性表、指标表、约束违规表和多目标权衡汇总。
2. 把候选方案转成 TWM 可理解的动作：每个方案变成一个带方案编号的候选动作，包含方案类型、影响范围、项目数量、收益指标、风险指标和来源信息。
3. 先做硬约束过滤：如果候选方案在可行性表中不是“合法可行”，或者约束违规表里有阻断/严重违规，就标记为“不可推荐”（技术载荷中可能显示为 `hard_blocked`）。这种方案可以展示给领导看原因，但不能被推荐。
4. 对每个候选方案调用模拟器：计算该方案下的规划收益、约束风险、可信度和证据状态。
5. 排序：排序不是只看收益。当前规则可以概括为 `收益 - 风险 + 可信度加分 - 不可推荐扣分 - 需要人工复核扣分`。因此收益高但违法或证据不足的方案，会被降级或阻断。
6. 形成选择说明：输出候选数量、合法可行数量、阻断方案、推荐方案、推荐理由和不能作为生产结论的边界。

现场可以这样举例：

> 如果一个方案收益分很高，但占用了永久基本农田或生态红线，规划器不会因为分高就推荐它，而是把它留在“阻断方案”里说明原因。真正推荐的方案必须先过硬约束，再看风险、收益和证据支撑。

必须讲清楚的边界：

1. 当前演示里的规划器主要是“候选方案消费者、审查器和排序器”，不是完整替代专业规划优化模型的方案生成器。
2. 如果接入外部优化器、科研优化算法或人工备选方案，TWM 可以负责统一审查、排序、解释和证据留痕。
3. 要证明“自动生成生产级最优方案”，还需要自然资源部门真实历史方案、真实审查结果、空间/时间留出验证和人工专家对照。

这一页要讲清楚的价值：
- 方案不是只按分数排序，而是同时考虑约束、风险、收益和证据支撑。
- 被阻断的方案也要展示原因，方便审查人员理解为什么不能选。
- 地图联动保证推荐结果可以被空间复核。

## 9. 回到数据证据：说明边界、基线和下一步真实数据

操作：
1. 切换到 `数据证据`。
2. 查看 `数据基础浏览器`。
3. 向下查看 `关键阻断项`、`完整数据清单`、`完整验证快照`、`问题-数据适配`、`来源报告`。
4. 查看 `生产声明` 和 `主张矩阵`。现场解释为“哪些能说、哪些不能说的边界表”。
5. 查看 `试点就绪矩阵`：重点看 `生产门槛`、合成数据不能替代生产验收、测试数据计划。
6. 查看 `规则样例覆盖`：重点看 `TWM-FARM-001`、`TWM-ECO-001`、`TWM-PLAN-001`、`TWM-URBAN-001` 是否有正例/反例样例，以及 `boundary_case` 缺口。
7. 点击 `基线对比`。

预期看到：
- `完整数据清单` 中包含 `twm_bishan_multi_admin_eval`。
- 文件清单中能看到 `parcel_current.geojson`、`synthetic_projects.geojson`、`tables/approval_records.csv`、`tables/rule_evaluation.csv` 等。
- `问题-数据适配` 中明确说明哪些输出安全、哪些不能承诺。
- `试点就绪矩阵` 显示当前总体仍受生产观察历史和政策动作标签阻断；`生产门槛` 不应显示为通过。
- `规则样例覆盖` 显示四类硬约束规则；现有演示/合成数据可支撑回归覆盖，但 `boundary_case` 缺口应被明确列出。
- `基线对比` 返回 TWM 和基线对比内容。

讲解要点：
> 最后一定要回到数据证据页，把能力边界说清楚。当前 TWM 证明的是端到端链路、可计算状态、规则-预测-方案闭环和证据台账；真实生产结论必须等自然资源部门权威数据接入后再验证。这里的“生产声明”“试点就绪矩阵”和“规则样例覆盖”，就是为了防止演示现场只讲能做什么，而不讲还缺什么。

这一页要讲清楚的价值：
- 数据证据台账：完整展示数据包、文件计数、生产/非生产边界、验证快照和来源报告。
- 能力边界：明确哪些能力已有演示数据支撑，哪些仍需要真实权威数据。
- 基线对比：避免只展示 TWM 自己的结果，必须能和人工 GIS、规则引擎或优化工具比较。

## 11. 收束语

> 这个原型现在重点证明三件事：第一，TWM 可以把同一批国土空间数据整理成可计算的业务快照，并和地图联动起来；第二，可以把规则命中、风险推演、方案比选和证据审计串成闭环；第三，它没有把演示数据当成权威结论，后续需要接入自然资源部门真实权威数据，才能做严谨的业务增益验证。

## 12. 人工验证失败时的停止条件

出现以下任一情况，应停止演示并记录问题：

1. `全量加载空间数据` 后地图没有出现空间图层。
2. `synthetic_projects.geojson` 单图层 `上图` 后地图没有出现项目空间图层。
3. `定位审查区` 与全量数据图层明显不在同一空间范围。
4. `操作推演` 主流程没有选择 `璧山多行政单元`。
5. `构建状态` 后没有对象数或关系数，或对象数/关系数小于等于 100。
6. `风险命中` 或 `推荐方案` 只显示状态文字，地图没有联动变化。
7. 数据证据中看不到 `twm_bishan_multi_admin_eval` 或完整数据清单。
8. `试点就绪矩阵` 或 `规则样例覆盖` 没有出现，或合成数据被显示为可满足生产验收。
9. `基线对比` 没有返回对比结果。
10. `技术载荷` 无法展开或没有 JSON 内容。
