# 城市宜居性分析（传统方法）演示脚本说明

版本日期：2026-07-07  
演示入口：`http://localhost:8000`  
演示页面：`工作台 -> 智能分析 -> 城市宜居性分析（传统方法）`  
适用场景：在 GIS Data Agent 中演示传统城市信息化方法基于同一套城市宜居性数据能够做到的分析深度，并作为后续 UWM 世界模型方法的公平基线。

## 1. 文档目的

本文档用于现场演示和内部复核，说明当前已经实现的“城市宜居性分析（传统方法）”功能：

1. 使用哪些真实本地数据；
2. 技术实现原理是什么；
3. 前端如何操作；
4. 预期看到哪些输出；
5. 这个传统方法能得出什么结论，不能得出什么结论。

这份文档只描述传统方法。它不是 UWM 世界模型能力说明，也不能把传统方法输出包装成反事实模拟、规划器优化或政策效果验证。

## 2. 演示核心口径

本功能回答的问题是：

> 基于当前已有的多源城市宜居性状态数据，重庆中心城区哪些行政单元宜居性短板更突出，应该优先纳入人工复核和治理关注？

传统方法的输出是：

```text
当前哪里差、差在哪些指标维度、哪些单元优先关注、可以给出哪些静态规则建议。
```

传统方法不输出：

```text
采取某个行动后未来会怎样、多步行动序列如何安排、空间外溢有多大、风险校正收益是多少、方案是否经过规划器搜索验证。
```

现场讲解时必须明确：这是“同一数据基础上的传统基线”，不是故意做弱的对照组。它代表常见城市信息化驾驶舱/指标大屏进一步做结构化后的能力上限：能汇总、能排序、能诊断短板，但仍然停留在当前状态解释。

## 3. 理论依据

传统方法下的城市宜居性分析不是凭空构造的指标大屏，它继承了此前 UWM 城市宜居性理论分析中的基础框架。需要衔接说明的是：同一套城市宜居性理论可以支撑“传统静态评价”和“UWM 世界模型评价”，但两者使用理论的深度不同。

此前理论文档包括：

```text
docs/reports/uwm_livability_theory_sources_and_standards_2026-07-05.md
docs/reports/uwm_livability_business_theory_2026-07-05.md
```

### 3.1 理论来源

城市宜居性不是由单一国家标准完整定义的。它更像一个复合评价框架，核心来自以下理论和标准来源：

| 理论/标准来源 | 对城市宜居性分析的支撑 |
| --- | --- |
| 城市环境质量与人类福祉 | 宜居性应同时看物理环境、居民福利、社会差异和空间分布 |
| 健康城市与健康社会决定因素 | 城市空间条件会影响居民健康、服务机会、活动机会和社会参与 |
| 城市规划与人口健康 | 土地利用、交通、密度、公共空间、空气污染和步行环境会共同影响健康与宜居性 |
| 15 分钟城市/15 分钟生活圈 | 日常服务和活动机会应在合理时间、距离和成本内可达 |
| 空间公平与环境正义 | 不能只看全市平均值，还要看低宜居区域、脆弱人群和高暴露人群是否处于不利状态 |
| WHO Healthy Cities 与 UN SDG 11 | 提供健康、安全、包容、韧性、可持续城市的宏观目标框架 |
| `GB 3095-2026 环境空气质量标准` | 支撑空气污染暴露、PM2.5 等环境健康指标口径 |
| `GB 50180-2018 城市居住区规划设计标准`、社区生活圈、城市体检类文件 | 支撑公共服务、生活便利性、居住环境和设施配套评价 |
| `GB/T 51346-2019 城市绿地规划标准`、`GB/T 51255-2017 绿色生态城区评价标准` | 支撑绿地、开放空间、生态环境和可持续评价 |

因此，传统方法下的城市宜居性评价可以被理解为：

```text
城市宜居性静态评价
= 环境健康风险
+ 公共服务可达性
+ 交通/活动便利性
+ 人口暴露公平性
+ 城市形态和开发强度平衡
```

### 3.2 理论到当前五个维度的映射

当前传统页面中的五个维度，与上述理论依据的映射关系如下：

| 当前传统维度 | 理论依据 | 当前实现中的观测变量 |
| --- | --- | --- |
| 公共服务可达性 | 15 分钟生活圈、居住区规划、公共服务均衡 | `service_gap_norm`、`essential_service_gap_norm` |
| 环境健康 | 健康城市、环境暴露、空气质量标准、绿地/热环境健康效应 | `heat_exposure_norm`、`tap_scene_pm25_mean_ugm3`、`gee_cams_pm25_ugm3` |
| 交通连通性 | 城市规划与人口健康、活动便利性、道路/慢行/公共交通可达性理论 | `osm_road_segment_count`、`osm_road_length_degrees_proxy`、`admin_graph_degree` |
| 人口暴露公平性 | 空间公平、环境正义、健康社会决定因素 | `exposure_priority_score`、`ghsl_population_proxy_sum` |
| 城市强度平衡 | 人居环境质量、城市形态、建成环境与服务承载关系 | `ghsl_built_surface_proxy_sum`、`osm_bbox_area_degrees2` |

这说明传统方法不是任意拼指标，而是把城市宜居性理论压缩成静态可解释指标体系。

### 3.3 传统方法的理论边界

传统方法的理论角色是“多指标综合评价”或“指标驾驶舱增强版”。它可以在理论框架下回答：

```text
当前哪些地方宜居性较低？
低宜居主要体现在哪些维度？
哪些行政单元应优先进入人工复核和治理关注？
```

但传统方法不能充分表达城市作为复杂巨系统的动态特征。它缺少：

```text
动作 a_t
状态转移 s_t -> s_t+1
空间外溢
多步规划
不确定性和风险校正收益
```

所以，同一套理论在传统方法中只落到“现状评价”，在 UWM 中才进一步落到：

```text
Renderer:  将多源数据渲染为城市世界状态
Simulator: 模拟行动条件下的状态变化
Planner:   搜索多步行动序列并比较反事实收益
```

这也是后续演示中传统方法和 UWM 最终输出不同的根本原因。

### 4.1 已直接进入传统方法的字段

当前传统方法直接使用或间接解释的字段如下：

| 数据来源 | 当前传统方法中的作用 |
| --- | --- |
| `admin_livability_target_complete_bbox` | 提供 `livability_need_score`，直接决定传统综合宜居性得分和静态优先级排序 |
| `admin_exposure_equity` | 提供 `exposure_priority_score`，进入人口暴露公平性诊断；也参与上游 `livability_need_score` 构建 |
| `admin_service_accessibility_complete_bbox` | 提供 `service_gap_norm`、`essential_service_gap_norm`、服务点数量，进入公共服务可达性诊断；也参与上游 `livability_need_score` 构建 |
| `ghsl_admin_alignment` | 提供 `ghsl_population_proxy_sum` 和 `ghsl_built_surface_proxy_sum`，进入人口暴露公平性和城市强度平衡诊断 |
| `gee_admin_environment` | 提供 `gee_cams_pm25_ugm3` 等环境代理，进入环境健康诊断 |
| `scene_aligned_gridded_air_quality_holdout` | 提供 `tap_scene_pm25_mean_ugm3` 和 `chap_pm25_ugm3` 等 PM2.5 场景数据；其中 TAP 场景 PM2.5 进入环境健康诊断，CHAP 锚点更多用于 renderer/holdout 校验 |
| `admin_spatial_adjacency_graph` | 提供 `admin_graph_degree`，进入交通连通性诊断，并为后续 UWM 空间外溢提供图结构 |
| `osm_mobility_network_proxy` + `osm_admin_mobility_crosswalk` | OSM 道路网络通过 crosswalk 投影为 `osm_road_segment_count`、`osm_road_length_degrees_proxy`、`osm_bbox_area_degrees2`，进入交通连通性和城市强度平衡诊断 |

需要特别说明：当前传统综合排序直接使用 `livability_need_score`。该分数在上游 `admin_livability_target_complete_bbox` 中由暴露公平性和服务可达性代理复合生成，权重为：

```text
exposure_norm               0.50
service_gap_norm            0.30
essential_service_gap_norm  0.20
```

后续传统页面中的五个维度用于解释、诊断、低分单元统计、短板标签和地图表达；它们扩展了现状解释，但不把传统方法升级成动态世界模型。

### 4.2 已接入但未直接进入传统静态评分的数据

`unicom_latent_mobility_graph` 当前没有直接进入传统方法的静态总分和维度得分。原因不是它对城市宜居性没有意义，而是：

1. 原始联通职住通勤数据缺少稳定的格网几何字典；
2. 当前只形成了无坐标潜在通勤图；
3. 缺少从通勤格网/OD 边到 36 个行政候选单元的可信空间 crosswalk；
4. 传统静态评分如果强行使用它，会把“活动联系强弱”混成不可复核的分数噪声。

因此，当前文档和页面把它标记为：

```text
unit_projection = not_projected_without_grid_to_admin_crosswalk
```

它仍然有价值，原因是：

- 对传统方法：作为数据基础披露和后续人工解释上下文，说明已有潜在活动联系数据，但当前不把它硬塞进静态分数；
- 对 UWM renderer：未来可在补齐空间 crosswalk 后成为城市活动状态的一部分；
- 对 UWM simulator：可用于构造通勤/活动强度对服务可达性、污染暴露和交通压力的影响；
- 对 UWM planner：可用于识别干预动作的潜在影响范围和外溢路径；
- 对证据门控：明确记录它的边界，防止把未投影数据包装成已验证结果。

所以，收集这类数据不是浪费。城市是复杂巨系统，UWM 需要比传统指标大屏更宽的数据基础。但在传统基线里，只有已经完成稳定空间对齐、字段含义清楚、能被复核的数据才进入当前静态分数或维度诊断。没有完成对齐的数据应保留为上下文和后续 UWM 能力储备，而不应为了“看起来用了所有数据”而强行计分。

### 4.3 数据应用原则

本演示采用以下原则：

1. 同一数据基础必须向传统方法和 UWM 共同开放；
2. 传统方法只使用能稳定投影到行政单元的当前状态字段；
3. 未投影、缺 crosswalk、缺观测校准的数据不进入静态分数；
4. 这些未直接计分的数据仍可用于 UWM 的 renderer、simulator、planner、外溢建模、状态预测或证据门控；
5. 不允许为了宣传“数据全用上了”而把不可复核的数据硬编码进分数。

数据覆盖复核口径：

- 暴露公平性、服务可达性、GHSL、GEE、PM2.5 网格、行政邻接图、OSM 行政交叉映射均覆盖 36/36 个行政单元；
- OSM 道路网络代理包含 42,058 个节点、45,468 条边，其中 45,449 条道路段完成行政单元分配，19 条未分配；
- 行政空间邻接图源数据包含 1,017 个节点、2,847 条边；
- `unicom_latent_mobility_graph` 当前保留为潜在流动网络数据，因缺少网格到行政单元的稳定 crosswalk，未在传统静态分数中直接使用。

## 5. 技术实现原理

### 5.1 后端实现位置

核心分析函数位于：

```text
data_agent/uwm/traditional_livability_analysis.py
```

API 路由位于：

```text
data_agent/api/uwm_traditional_livability_routes.py
```

前端 tab 位于：

```text
frontend/src/components/datapanel/TraditionalLivabilityTab.tsx
```

页面注册位置：

```text
frontend/src/components/DataPanel.tsx
```

### 5.2 分析流程

传统方法的完整流程如下：

```text
多源场景 JSON
  -> 读取 36 个行政单元 state_vector
  -> 对静态指标做归一化和维度汇总
  -> 计算当前宜居性分数、需要度、等级
  -> 按当前需要度排序
  -> 生成短板标签
  -> 生成静态规则建议
  -> 输出表格、KPI、维度条形图和地图图层
```

它的关键特征是“静态当前状态分析”：

- 输入是当前场景状态；
- 输出是当前分数、当前短板和当前优先级；
- 不模拟行动后的未来状态；
- 不搜索多步行动序列；
- 不计算空间外溢；
- 不评估反事实收益。

### 5.3 综合得分和排序

每个行政单元的综合宜居性得分来自场景中的 `livability_need_score` 的反向值：

```text
traditional_livability_score = 1.0 - livability_need_score
static_livability_need_score = livability_need_score
```

排序规则是：

```text
static_livability_need_score 越高，静态治理优先级越高。
```

也就是说，传统方法优先找“当前状态下最需要关注的地方”，而不是找“投入某个行动后收益最大的地方”。

### 5.4 指标维度体系

页面展示 5 个静态诊断维度：

| 维度 | 权重 | 使用字段 | 含义 |
| --- | ---: | --- | --- |
| 公共服务可达性 | 0.30 | `service_gap_norm`、`essential_service_gap_norm` | 服务缺口越小，得分越高 |
| 环境健康 | 0.25 | `heat_exposure_norm`、`tap_scene_pm25_mean_ugm3`、`gee_cams_pm25_ugm3` | 热暴露和 PM2.5 越低，得分越高 |
| 交通连通性 | 0.20 | `osm_road_segment_count`、`osm_road_length_degrees_proxy`、`admin_graph_degree` | 道路和邻接连通越强，得分越高 |
| 人口暴露公平性 | 0.15 | `exposure_priority_score`、`ghsl_population_proxy_sum` | 暴露压力越低，得分越高 |
| 城市强度平衡 | 0.10 | `ghsl_built_surface_proxy_sum`、`osm_bbox_area_degrees2` | 建成强度与空间尺度越平衡，得分越高 |

注意：当前实现中，这些维度主要用于短板诊断、维度均值、低分单元统计和页面解释；综合排序直接使用同一场景中已经构建好的 `livability_need_score`。这符合传统方法作为基线的定位：它不重新训练模型，也不运行模拟器，只消费当前状态指标并做解释性聚合。

### 5.5 短板标签规则

短板标签采用规则阈值：

- `livability_need_score >= 0.75`：标记为 `综合宜居性高风险`；
- 任一维度得分低于 0.4：标记该维度对应短板；
- 如果没有明显短板：标记为 `静态观察`。

标签示例：

```text
综合宜居性高风险
公共服务可达性短板
环境健康短板
交通连通性短板
人口暴露公平性短板
城市强度平衡短板
```

### 5.6 静态行动建议

传统方法根据短板标签映射到规则化建议：

| 短板标签 | 静态建议 |
| --- | --- |
| 综合宜居性高风险 | 纳入人工复核重点清单 |
| 公共服务可达性短板 | 补齐基本公共服务设施 |
| 环境健康短板 | 开展热暴露与空气质量治理 |
| 交通连通性短板 | 提升道路与公共交通连接 |
| 人口暴露公平性短板 | 开展人口暴露与公平性精细化排查 |
| 城市强度平衡短板 | 校核开发强度与公共空间配置 |

这些建议是静态规则建议，不代表系统已经证明该行动一定最优，也不代表行动后的未来收益已经被估计。

### 5.7 地图图层输出

点击“发送到地图”后，后端会：

1. 读取行政单元 GeoJSON；
2. 将传统方法得分、排名、短板标签写入行政单元属性；
3. 生成 `uwm_traditional_livability_static.geojson`；
4. 将地图更新写入当前用户的 pending map update；
5. 前端读取 `/api/map/pending` 并调用地图联动函数。

图层分类字段为：

```text
static_priority_class
```

分类含义：

| 分类 | 含义 |
| --- | --- |
| 高优先级 | 当前 Top N 重点单元 |
| 中优先级 | 当前排序中等偏高的单元 |
| 一般 | 其余单元 |

## 6. API 与鉴权

当前页面使用两个接口：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/uwm/traditional-livability?top_n=8` | 获取传统方法分析结果 |
| POST | `/api/uwm/traditional-livability/map` | 生成并发送静态优先级地图图层 |

这两个接口都需要登录态。未登录直接访问 API 返回 `401 Unauthorized` 是预期行为，不应解释为接口没有部署。

`top_n` 支持 1 到 20，前端提供 5、8、12、16、20 五个选项。

## 9. 客户演示建议话术

开场：

> 这里先展示传统方法。它和后面的 UWM 使用同一份城市宜居性数据，不是两套数据，也不是故意让传统方法少用数据。传统方法代表常见指标驾驶舱进一步结构化后的能力：汇总现状、发现短板、排序重点区域。

看 KPI：

> 当前 36 个行政单元的综合宜居性得分约为 0.434，等级为 D。这个数字说明整体压力偏高，但传统方法只能说明当前状态偏弱，不能说明采取哪个行动后改善最大。

看维度：

> 维度拆解显示，公共服务可达性是最弱维度，低分单元有 29 个。交通连通性和城市强度平衡也存在系统性短板。这是传统方法比较有效的地方：把多源数据转成可读的指标解释。

看排名：

> 九龙坡区九龙镇是当前静态优先级最高的单元，宜居得分为 0，短板覆盖公共服务、环境健康、交通和人口暴露公平性。这个结论适合进入人工复核清单。

看地图：

> 点击发送到地图后，系统把静态优先级变成空间图层。客户可以直接看到高优先级区域在哪里，而不是只看表格。

收束：

> 到这里，传统方法已经做到比较完整：多源数据接入、静态综合评分、维度诊断、优先级排名、规则建议和地图表达。但它没有模拟器、没有规划器，也没有反事实评估。因此它的最终结果仍是“问题清单”，不是“经过模拟和规划验证的治理方案”。

## 10. 与 UWM 后续演示的衔接口径

传统方法演示结束后，可以自然过渡：

> 刚才传统方法已经告诉我们“哪里有问题”。但城市管理更难的问题是“做什么、先做哪个、做完以后未来状态如何、周边是否有外溢、方案风险多大”。这些问题不是指标大屏能够直接回答的，所以后面进入 UWM 世界模型：通过 renderer 构造城市状态，通过 simulator 预测行动条件下的状态变化，再通过 planner 搜索多步行动序列。

对照关系：

| 对比项 | 传统方法 | UWM 世界模型 |
| --- | --- | --- |
| 数据基础 | 同一套多源城市宜居性场景 | 同一套多源城市宜居性场景 |
| 核心输入 | 当前状态指标 | renderer 构造的世界状态 |
| 核心计算 | 静态归一化、评分、排序、规则标签 | 模拟器 rollout、规划器搜索、风险收益评估 |
| 最终输出 | 当前问题清单和静态建议 | 行动序列、未来状态、外溢、风险校正收益、证据边界 |
| 是否有反事实 | 无 | 有 |
| 是否有规划器 | 无 | 有 |
| 是否证明行动优越 | 无 | 需要通过同数据基线比较证明 |

## 11. 异常处理和现场检查

### 11.1 页面打不开

检查：

1. 确认访问的是 `http://localhost:8000`，不是 `http://localhost:8010`；
2. 确认 Docker 容器已经启动；
3. 确认浏览器没有缓存旧入口。

### 11.2 API 返回 401

说明：

```text
未登录直接访问 /api/uwm/traditional-livability 返回 401 Unauthorized 是预期行为。
```

处理：

1. 先通过页面登录；
2. 再进入 tab；
3. 不要把 401 解释成接口未部署。

### 11.3 页面没有数据

检查：

1. Docker 镜像中是否存在 `/app/data/uwm_public_proxy/`；
2. 本地是否存在 `data/uwm_public_proxy/chongqing_central/...`；
3. 后端环境变量 `UWM_TRADITIONAL_LIVABILITY_SCENE_PATH` 是否被错误覆盖；
4. 后端日志是否出现 JSON 读取错误。

### 11.4 地图没有图层

检查：

1. 是否已经登录；
2. 是否点击了 `发送到地图`；
3. 是否看到“已发送传统方法静态优先级图层到地图”的提示；
4. `/api/map/pending` 是否有待处理 map update；
5. 行政单元 GeoJSON 是否存在并能按区县/乡镇匹配。

## 13. 演示结论

传统方法的城市宜居性分析可以认为已经形成一条完整的传统基线演示链路：

```text
真实本地多源数据
  -> 当前状态静态评分
  -> 维度短板诊断
  -> 静态优先级排名
  -> 规则建议
  -> 地图图层表达
  -> 能力边界说明
```

它对客户的价值是：让客户直观看到传统城市信息化方法在同一数据基础上能够做到什么程度。

它的边界也必须明确：传统方法最终输出的是“当前问题清单和静态建议”，不是“经过模拟器和规划器证明更优的行动方案”。后续 UWM 的优势必须建立在同一数据、同一场景、同一城市宜居性任务之上，证明它能输出传统方法无法输出的反事实规划结果。
