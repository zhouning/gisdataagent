# 自然资源本体应用客户演示讲稿

- 文档版本：V1.1
- 修订日期：2026-08-05
- 本次修订：补充自然资源本体模型在演示中的作用、示例链路及准确表述边界
- 演示应用：GIS Data Agent
- 本体版本：自然资源“一张图”本体 V2.0.1
- 演示数据：规划院提供数据样例及 Demo 系统功能演示建议
- 场景范围：重庆市璧山区福禄镇和平村、斑竹村
- 结论边界：辅助预审，不替代法定审批或行政决定

## 一、演示主线

本次不按十个菜单逐项展示，而是用一条业务闭环说明时空数据底座如何变得更好用：

> 规划地块从什么状态变成什么状态，属于哪一种自然资源业务过程，是否命中已注册的空间约束，还缺少什么审批证据？

和平村负责演示地块级用地转换和空间约束辅助预审；斑竹村负责演示规划前后土地利用结构变化，以及统计指标如何回到具体地块和本体状态。

### 页面导航说明

本手册中的“数据治理”“能力闭环”不是 GIS Data Agent 的一级页面，也不是“平台运营”下的治理功能。完整入口是：

> 智能分析 > 本体应用 > 数据治理（或能力闭环）

进入“本体应用”后，在白色工作区中找到 `Cognitive Runtime` 执行链；其下方依次排列“分析结论、语义证据、数据治理、能力闭环”四个内部页签。屏幕较窄时，先横向滚动“智能分析”的顶部页签栏找到“本体应用”。

## 二、本体模型在本演示中如何发挥作用

### 1. 本体不是展示图，而是业务语义和规则合同

本体在本演示中不负责保存全部图斑，也不替代 GIS 引擎计算面积。它位于数据与智能体之间，为原始字段、地类代码、空间对象、业务过程、管控规则和证据材料提供统一且版本化的领域语义。

演示中的实际处理链路是：

> 原始数据与字段 → 本体概念对齐 → 地块状态转换识别 → 规则和证据要求 → GIS 空间计算 → Agent 组织可解释结论

本体回答“数据表示什么、对象之间是什么关系、一次变化属于什么业务过程、需要满足什么约束”；GIS 引擎回答“在哪里、相交多少”；Agent 回答“用户问的是什么、应该调用哪些能力、怎样解释结果”。

### 2. 五项核心作用

| 本体作用 | 在本演示中的具体体现 | 没有本体时的局限 |
|---|---|---|
| 建立统一语义目标 | 将 `TDGHDL.BSM` 对齐到 `LandParcel` 的实体标识，将 `JQDLMC`、`GHDLMC` 对齐到土地利用的源状态和目标状态 | 系统只能认识表名、字段名和代码，跨系统后需要重复编写解释逻辑 |
| 识别状态与业务过程 | 根据源状态和目标状态，将变化解释为农业结构调整、建设占用、土地复垦、土地整治或一般土地利用转换 | 只能得出“两个字段值不同”，不能说明变化的业务含义 |
| 提供规则和证据结构 | 将红线、地灾、林地等表达为对地块转换的约束，并规定建设占用需要审批文件等证据 | 空间相交结果与业务规则、审批材料彼此分散，容易把“未发现冲突”误报成“合规” |
| 组织可追溯证据链 | 用 `hasSourceState`、`affectsParcel`、`hasTargetState`、`constrainedBy`、`authorizedBy` 等关系连接结论、对象、过程、约束和依据 | 只能看到结果数字，难以追溯为什么得出该结论以及依据来自哪里 |
| 形成智能体稳定知识接口 | Agent 不必依赖某个数据表的临时字段，而是围绕“地块、状态、转换、约束、证据”等稳定概念理解问题和组织工具调用 | 数据表或部门术语改变后，提示词和应用逻辑容易漂移，跨部门复用成本高 |

### 3. 一个地块如何被本体解释

以某一规划图斑“规划前为旱地、规划后为村居住用地”为例，原始数据只提供三个关键事实：

- `BSM`：图斑标识；
- `JQDLMC = 旱地`：规划前地类；
- `GHDLMC = 村居住用地`：规划后地类。

经过本体语义对齐后，该图斑被组织为：

> 地块实体 `LandParcel` → 源状态“耕地利用状态” → 转换过程“建设占用” → 目标状态“建设用地利用状态”

“建设占用”不是简单标签，而是带有业务约束的过程类型。它要求进一步检查：

- 是否与生态保护红线、历史文化保护要素等禁止性或保护性范围相交；
- 是否命中地质灾害、林地等条件性约束；
- 是否通过 `authorizedBy` 关联审批文件；
- 分析结论能否通过来源文件、字段、本体 URI、规则和版本哈希进行追溯。

因此，一个没有命中空间冲突但缺少审批文件的建设占用图斑，系统显示“材料待补”，而不是“初筛通过”。这正是本体把空间分析提升为领域业务分析的关键体现。

### 4. 本体如何支持统计分析和跨部门协同

在斑竹村场景中，结构调整表和规划图斑原本是两个不同粒度的数据来源。本体将“旱地、园地、林地、宅基地”等术语归入稳定的土地利用状态体系，使统计表中的总量变化能够与具体图斑上的状态转换建立一致解释。

跨部门扩展时，其他部门不必接受自然资源部门内部的全部表结构或实体编码，只需将自己的术语和数据字段映射到共享概念。例如，农业、林业、生态环境和应急管理数据可以分别对齐到耕地、林地、生态约束和地灾约束，再由 MMFE 执行映射与冲突处理。这样保留各部门原有数据体系，同时在语义层形成可协同的共同语言。

### 5. 技术职责和演示边界

| 组件 | 本演示中的职责 |
|---|---|
| 自然资源本体 V2.0.1 | 定义实体、状态、过程、关系、规则、证据语义及稳定 URI |
| MMFE | 按本体提供的目标语义执行字段和术语对齐，保留未决映射与冲突 |
| GIS 引擎 | 在源投影坐标系中执行几何修复、空间叠加和面积计算 |
| SHACL | 表达状态转换记录、来源、法律依据和审批证据的完整性约束 |
| Agent | 解析业务问题、规划执行步骤、调用工具并组织证据化解释 |

当前客户演示使用与本体 V2.0.1 哈希绑定的不可变演示包。状态映射、转换识别和空间结果在演示数据构建阶段按照本体语义及规则确定性编译，运行时校验本体版本和数据文件哈希后读取结果。因此，应表述为“本体约束并驱动演示语义链路”，不表述为“每次点击都由大模型或 OWL 推理器临时生成全部结论”。

建议面向客户使用以下表述：

> 在这个演示中，本体是时空数据底座的业务语义内核。它把不同来源的字段和代码翻译成统一的地块、状态、过程、约束和证据关系；GIS 引擎据此完成空间计算，智能体据此理解问题并解释结果，使分析从“查到了哪些数据”升级为“这些数据在业务上意味着什么、为什么得到这个结论、还缺少什么依据”。

## 三、30 分钟安排

### 0-3 分钟：传统模式的问题

打开 GIS Data Agent 的“智能分析 > 本体应用”。

讲解要点：

- 传统数据底座能够保存和展示数据，但字段、代码、业务规则和证据仍分散在不同系统和文档中。
- 地理实体编码回答“它是谁”；本体进一步回答“它是什么、处于什么状态、发生了什么过程、受什么规则约束、依据在哪里”。
- 本体不是新的业务系统菜单，也不是把表名和功能名改造成类。

### 3-8 分钟：数据汇聚与语义注册

在“本体应用”工作区中，找到 `Cognitive Runtime` 执行链下方的四个内部页签，点击第三个“数据治理”。不要进入“平台运营”下的治理功能。

讲解要点：

- 本次真实汇聚 10 个来源资产，包含 Shapefile 和 Excel。
- 和平村 902 个规划地块、斑竹村 1,555 个规划地块均保留源坐标系、源字段和文件哈希。
- `TDGHDL.JQDLMC` 映射到转换的源状态，`TDGHDL.GHDLMC` 映射到目标状态，`TDGHDL.BSM` 映射到地块身份。
- 强调这里不是简单修改字段名称，而是把来源字段放入“地块实体—源状态—转换过程—目标状态”的统一语义结构。
- 21 类地类术语已映射，水库水面、河流水面、特殊用地 3 类进入治理待办，没有静默猜测。
- 和平村项目台账有 16 项，但 `TDGHDL.XMMC` 全为空，因此系统明确显示 0/16 空间关联，而不是伪造项目位置。

### 8-16 分钟：和平村用地转换辅助预审

选择“用地转换辅助预审”，执行语义分析。

讲解要点：

- 902 个规划地块中，445 个地类发生变化，变化面积 79.73 公顷。
- 本体把变化表达为“地块实体 + 源状态 + 转换过程 + 目标状态”，避免把土地永久固化为某一类别。
- 以“旱地变为村居住用地”为例，说明系统先对齐为“耕地利用状态变为建设用地利用状态”，再识别为“建设占用”过程。
- 实际识别出农业结构调整、建设占用、土地复垦、土地整治和一般土地利用转换。
- GIS 引擎在源投影坐标系中执行真实叠加和面积计算。
- 25 个变化地块命中禁止性或保护性空间约束。
- 108 个地块涉及建设占用但未关联审批文件，空间上未发现冲突也不能显示为合规，只能标记“材料待补”。
- 说明“材料待补”来自建设占用过程的证据要求，而不是地图颜色或大模型主观判断。
- 312 个地块命中地灾或高郁闭度林地等条件约束，进入跨部门复核。

点击代表性地块右侧证据按钮。

讲解要点：

- 页面可追溯到 `LandParcel`、源状态、转换过程、目标状态及 `constrainedBy`、`authorizedBy` 等关系。
- 每个空间命中显示约束类型、名称和真实相交面积。
- 每个判断绑定本体 V2.0.1、演示包版本和源资产 SHA-256。

### 16-21 分钟：斑竹村土地利用结构调整

切换“土地利用结构调整”，执行语义分析。

讲解要点：

- 1,555 个规划地块中，559 个发生变化，变化面积 87.24 公顷。
- 结构调整表显示农用地从 625.63 公顷增至 634.69 公顷，净增 9.06 公顷。
- 旱地增加 16.21 公顷，园地增加 1.73 公顷。
- 林地减少 3.31 公顷，坑塘水面减少 4.20 公顷。
- 宅基地（村居住用地）减少 12.20 公顷。
- 统计变化通过本体状态与 559 个规划变化图斑关联，既能看总量，也能回到空间对象。
- 强调本体提供跨统计表与空间图斑共享的状态语义，使总量指标能够回到具体对象和转换过程。

### 21-25 分钟：质量、证据和版本治理

回到“本体应用”工作区，点击 `Cognitive Runtime` 执行链下方第三个内部页签“数据治理”。

讲解要点：

- 系统检查 CRS、几何、地块标识、规划前后状态、语义映射、项目关联和审批证据。
- 本体包、演示数据包、源文件分别版本化；本体哈希不匹配或数据文件被改写时，运行时拒绝加载。
- 质量警告形成治理任务，而不是被智能体隐藏。

### 25-28 分钟：总体架构与跨部门扩展

在同一位置点击第四个内部页签“能力闭环”。

讲解要点：

- 数据层承载基础地理、规划地类、管控边界和项目台账。
- 语义层以本体为内核，定义跨数据源共享的实体、状态、过程、规则、角色和证据语义。
- MMFE 执行实际语义融合，本体为其提供目标语义和约束。
- GIS 引擎负责坐标转换、空间叠加和面积计算。
- Agent 负责问题理解、任务规划、工具调用和证据解释。
- 应用层可面向规划审查、自然资源业务协同及跨行业场景复用同一语义底座。

### 28-30 分钟：总结

建议收束表述：

> 本体建设的价值不是增加一个图谱页面，而是让基础地理数据从“可看、可查”升级为“可理解、可计算、可解释、可协同”的时空数据底座。它让智能体有稳定的领域知识结构，让跨部门数据有可对齐的语义目标，也让每个分析结论能够回到规则、数据和版本证据。

## 四、十项能力对应关系

| 数据中心能力 | 本场景中的落点 |
|---|---|
| 数据汇聚 | Shapefile、Excel 多源资产统一注册 |
| 数据治理 | 术语映射及项目空间关联缺口显式管理 |
| 数据质检 | CRS、几何、标识、状态、映射和证据规则校验 |
| 数据展示 | 规划地块、转换过程和管控边界联动地图 |
| 数据分析 | 规划前后状态转换和空间叠加 |
| 数据分发 | 认证只读 GeoJSON 和版本化证据包 |
| 数据安全 | 认证 API、来源追踪和用途范围声明 |
| 全流程管理 | 问题解析到证据解释的六步执行链 |
| 数据反馈 | 未映射术语、未关联项目和缺失材料形成治理待办 |
| 更新维护 | 本体、演示包和源文件哈希独立版本化 |

## 五、演示注意事项

- 不表述“系统已经完成法定合规审查”，统一使用“辅助预审”“空间初筛”“条件复核”。
- 不宣称重点项目已经定位到具体图斑；当前源数据缺少可靠项目空间关联。
- 不把本体描述成空间计算引擎；叠加和面积由 GIS 引擎完成。
- 不把 MMFE 描述成本体；MMFE 是依据本体执行语义融合的引擎。
- 不只展示漂亮图谱，要始终回到业务问题、规则判断和来源证据。
- 不表述“每次点击都在线执行完整 OWL 推理”；当前演示结果是在构建阶段按本体语义和规则确定性编译，并在运行时进行版本与哈希校验。
