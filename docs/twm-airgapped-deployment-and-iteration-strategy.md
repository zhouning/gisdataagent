# TWM 在物理隔离内网环境下的部署与持续迭代策略

日期：2026-06-21

## 1. 背景问题

TWM（Territory World Model，地理空间世界模型）要真正成为自然资源治理场景中的可信能力，必须接触真实权威数据，包括国土调查、年度变更调查、规划“一张图”、用途管制、审批监管、执法督察、人工复核结论和历史变化记录等。

但自然资源真实权威数据具有明显的敏感性和安全边界，很多数据只能在物理隔离内网或专有环境中使用，不能进入外网研发环境。这形成了一个现实悖论：

- 没有真实权威数据，TWM 很难证明准确性、可靠性和业务可用性；
- 但在没有形成可部署原型系统之前，又很难进入真实权威数据环境；
- 即使进入内网环境，真实数据通常也不能导出，外网研发团队无法直接看见数据细节。

因此，TWM 的工程形态不能设计成依赖云端服务或外网在线训练的模式，而必须设计为：

> 外网开发能力，内网产生证据；真实数据不出域，代码、模型、规则和验证工具进域。

## 2. 推荐系统形态

TWM 最适合的形态不是云端 SaaS，也不是单机演示程序，而是：

> 物理隔离内网可部署的 TWM 一体化验证与迭代平台。

该平台应支持在外网研发环境中持续开发代码、算法、测试框架和合成验证数据，然后以离线制品包的形式交付到内网环境。在内网环境中接入真实权威数据，完成状态构建、模型训练、历史回放、因果校准、规划推演、人工复核和审计报告生成。

## 3. 三层环境划分

| 环境 | 主要作用 | 是否接触真实权威数据 | 关键要求 |
|---|---|---|---|
| 外网研发环境 | 开发代码、算法、接口、文档、合成数据、公开数据验证 | 不接触 | 快速迭代、自动化测试、合成压力测试 |
| 制品交付环境 | 生成 Docker 镜像、离线安装包、数据库迁移、模型包、测试包 | 不接触 | 可复现构建、版本签名、依赖封装 |
| 物理隔离内网环境 | 接真实数据、构建 TWM state、训练、验证、审计、人工复核 | 接触 | 数据不出域、审计留痕、离线运行、版本可追溯 |

这种划分的核心价值是：外网研发不需要接触敏感数据，内网也不需要依赖外部网络服务。TWM 的持续迭代依靠“离线制品进域”和“脱敏指标反馈出域”完成。

## 4. 离线交付包的组成

TWM 应被打包为可离线部署的一体化工程包，至少包括以下内容：

- TWM API 服务；
- TWM agent toolset；
- PostGIS / PostgreSQL 数据库；
- MinIO 或兼容对象存储；
- Spark / Sedona / Iceberg 等可选大数据组件；
- TWM 前端管理界面或 ArcGIS 风格业务验证界面；
- 数据标准、规则库、本体语义层和 MMFE 语义融合组件；
- TWM 状态构建器、模拟器、规划器、因果校准和 SCCA 证据接入模块；
- 模型训练、评估和版本对比 runner；
- 数据库迁移脚本；
- 合成测试数据和冒烟测试脚本；
- 内网日志、审计和验证报告导出服务。

交付形式应优先支持：

- Docker Compose 离线包；
- Kubernetes 离线部署包；
- 镜像 tar 包；
- Helm chart 或等价部署模板；
- 离线依赖包和初始化脚本；
- 数据库 schema migration 包；
- 版本说明、模型卡、规则卡和验证说明。

## 5. 数据与制品边界

TWM 必须严格区分“数据出域”和“制品进域”。

### 5.1 不应出域的内容

以下内容原则上不应离开物理隔离内网：

- 原始自然资源空间数据；
- 真实地块、图斑、项目、审批和监管记录；
- 可反推具体空间位置的坐标、边界、地块编号和项目编号；
- 真实审批材料、复核意见和执法线索；
- 带有敏感空间粒度的训练样本；
- 未脱敏的错误样本和空间失败案例。

### 5.2 可以进域的内容

外网可以向内网交付：

- TWM 代码版本；
- Docker 镜像；
- 数据库迁移脚本；
- 模型结构和训练脚本；
- 规则模板和标准契约；
- 合成数据和公开数据测试包；
- 验证 runner；
- 前端界面；
- 文档和部署脚本。

### 5.3 可控出域的反馈内容

在合规允许前提下，内网可以导出脱敏诊断信息，例如：

- 指标级评估结果；
- false allow / false block 统计；
- 规则命中类型分布；
- 模型版本对比结果；
- validation report 的脱敏摘要；
- claim ladder 等级；
- 不含坐标和对象编号的错误类型统计；
- 不含原始数据的空间分组汇总；
- 人工复核通过率和驳回类型统计。

这些反馈不用于还原真实数据，而用于指导外网研发环境改进下一版代码、规则、模型和验证逻辑。

## 6. Contract-first 数据接入策略

TWM 不应直接依赖某个地方的原始库表结构，而应依赖标准化的数据契约。

核心契约包括：

- MMFE semantic product；
- TWM state input；
- observed history schema；
- policy history schema；
- rule evidence schema；
- review task schema；
- validation report schema；
- selected plan evaluation bundle schema；
- SCCA causal evidence report schema。

真实数据接入应由内网 adapter 完成：

```text
真实业务库 / 文件 / 图层
  -> 内网 adapter
  -> 数据标准和语义层解析
  -> MMFE 语义融合产品
  -> TWM state input
  -> TWM 状态构建与验证
```

这种方式可以避免 TWM 主体被某个地方的库表结构绑定，也能让不同地区、不同司局、不同业务系统在不暴露原始数据结构的情况下接入 TWM。

## 7. 内网持续迭代闭环

内网部署后的 TWM 应形成如下闭环：

```text
真实历史数据
  -> TWM state 构建
  -> 规则审计
  -> 行动条件预测
  -> 规划方案排序
  -> 反事实推演
  -> SCCA / 因果校准
  -> validation report
  -> claim ladder
  -> 人工复核
  -> 脱敏指标反馈
  -> 下一版本外网研发
```

每一次升级都应自动比较：

- 是否降低 false allow；
- 是否增加 false block；
- 是否改善规划排序；
- 是否破坏硬约束；
- 是否提升历史回放拟合；
- 是否改善 SCCA / 因果校准；
- 是否提高人工复核认可度；
- 是否使 claim ladder 等级提升；
- 是否引入新的规则风险或审计缺口。

## 8. 版本化和审计要求

TWM 在内网环境中必须做到全链路版本化。

至少需要记录：

- 数据版本；
- 标准版本；
- 规则版本；
- 本体和语义层版本；
- MMFE 融合版本；
- TWM state 构建版本；
- simulator 版本；
- planner 版本；
- SCCA / causal calibration 版本；
- validation report 版本；
- claim ladder 结果；
- 人工复核结果；
- 模型训练参数；
- 模型评估指标；
- 部署制品版本。

这可以保证即使真实数据不能离开内网，系统仍然可以在内网持续积累可信证据，并且每次模型和规则升级都能被审计、回滚和比较。

## 9. 内网验证 runner

为了适应严格网络环境，TWM 应提供标准化验证命令或页面，例如：

```bash
run_twm_validation \
  --project <project_id> \
  --observed-history <observed_history.csv> \
  --policy-history <policy_history.csv> \
  --rule-version <rule_version> \
  --output validation_report.json
```

该 runner 应输出：

- TWM state 构建报告；
- 规则审计报告；
- 预测和反事实推演结果；
- selected plan evaluation bundle；
- SCCA causal evidence report；
- validation report；
- claim ladder；
- 人工复核任务清单；
- 脱敏诊断摘要；
- 模型版本对比结果。

长期看，应同时支持命令行、API 和前端页面三种方式。

## 10. 对当前 TWM roadmap 的含义

基于当前 TWM 已完成的工程基础，下一阶段重点不应继续扩展过多概念，而应围绕内网可部署和可验证能力推进。

优先级建议如下：

1. 完成本机 Docker 化端到端部署；
2. 打通 TWM API、数据库、对象存储、前端和 agent toolset；
3. 提供离线部署包生成脚本；
4. 完成真实 observed history / policy history 的内网 adapter 契约；
5. 完成内网 validation runner；
6. 完成脱敏诊断报告导出机制；
7. 完成模型、规则和验证结果的版本比较；
8. 完成 ArcGIS 风格或自然资源业务人员可操作的人工验证界面。

## 11. 最小可用形态

在进入真实权威数据环境之前，TWM 最小可用形态应达到：

- 一键或半自动离线部署；
- 不依赖外网服务；
- 能接入 MMFE semantic bundle；
- 能构建 TWM state；
- 能执行规则审计；
- 能运行 forecast、beam plan、counterfactual rollout；
- 能生成 selected plan evaluation bundle；
- 能接入 SCCA causal evidence；
- 能生成 validation report 和 claim ladder；
- 能导出脱敏诊断摘要；
- 能记录版本和审计日志。

达到这个形态后，TWM 才更适合被带入物理隔离内网，在真实权威数据上完成历史回放、专家复核和生产可用性验证。

## 12. 结论

TWM 在涉密敏感自然资源数据条件下的正确工程路线，不是等待真实数据开放，也不是试图把真实数据拿到外网，而是把系统设计成可进域、可离线运行、可内网验证、可脱敏反馈、可版本化升级的工程平台。

核心原则可以概括为：

> 数据不出域，制品进域；内网出证据，外网改能力；通过标准契约、验证报告和脱敏诊断形成持续迭代闭环。

这一路线能够同时满足两类要求：

- 自然资源真实权威数据的安全合规要求；
- TWM 从原型系统走向可信、可审计、可持续升级的工程要求。
