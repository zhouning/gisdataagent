# GIS Data Agent 本体模型与数据模型的关系

## 结论

在 GIS Data Agent 中，本体模型和数据模型不是同一个东西，也不是简单的上下级替代关系。

**数据模型负责“数据如何组织和存储”，本体模型负责“这些数据在业务上代表什么、如何理解和推理”。二者通过受控映射连接。**

```text
数据库 / API / 文件
        ↓
CDM / LDM / PDM 数据模型
        ↓
表、字段、外键、几何字段、值域的映射
        ↓
本体模型：类、属性、关系、约束、语义
        ↓
Gold 语义视图 / Agent 查询 / 空间分析 / 结果解释
```

## 1. 两者各自解决什么问题

| 方面 | 数据模型 | 本体模型 |
|---|---|---|
| 主要问题 | 数据放在哪里、字段是什么类型 | 数据对象具有什么业务含义 |
| 核心对象 | 表、字段、主键、外键、索引、接口字段 | 类、属性、关系、继承、状态、角色、约束 |
| 空间内容 | 几何类型、SRID、空间索引 | “位于”“覆盖”“邻接”“服务范围”等空间语义 |
| 数据库关系 | 描述可以怎样 JOIN | 说明 JOIN 后业务上代表什么关系 |
| 版本管理 | 表结构或接口结构快照 | 语义版本、稳定 URI、变更影响、审阅状态 |
| 使用者 | ETL、数据库、API、数据工程 | Agent、语义检索、自然语言理解、解释和治理 |

因此：

- 数据模型知道 `building_status` 是一个 `varchar` 字段；
- 本体模型知道它表示“建筑物的物理状态”，并且可能只能取某些状态值；
- 映射层负责确认这个字段确实对应本体中的某个属性。

## 2. GIS Data Agent 中的具体落地

### 数据模型侧

以 DMT 为例，数据模型来源于数据字典、接口样本和结构资料，形成：

- CDM：概念实体和业务域；
- LDM：实体、字段、关系和规范主键；
- PDM：PostgreSQL/PostGIS 表、字段类型、空间字段、索引和 DDL；
- 源对象目录、源字段目录、源关系目录；
- XMI、模型快照和 Gold 语义视图契约。

DMT 当前资料中有 972 个源对象、24,307 个源字段，规范层有 79 个实体、1,339 个规范字段和 223 条规范关系。这些首先是结构模型和数据目录，不等于已经确认的业务本体。

相关资料见 [DMT 数据模型说明](../customer/dmt_data_model_v1/README.md)。

### 本体侧

本体运行时管理：

- 领域类，例如建筑、地块、道路、设施、资产、检查、IoT 设备；
- 数据属性，例如建筑用途、状态、面积、观测时间；
- 对象关系，例如建筑位于地块、资产接受检查、设备关联资产；
- 几何语义、值域、状态和约束；
- 稳定 ID、URI、版本、哈希和溯源；
- 本体对象与源表、源字段之间的映射。

当前本体由 `ontology_key` 隔离管理。自然资源本体和 DMT 本体是两个独立 profile：

- `natural-resource-one-map`：自然资源本体，当前 246 个领域类；
- `abu-dhabi-dmt-gis`：DMT 城市与市政本体，当前 79 个领域类。

注册和隔离逻辑见 [`registry.py`](../../data_agent/ontology/registry.py)，本体包读取和映射读取见 [`package_reader.py`](../../data_agent/ontology/package_reader.py)。

运行时优先使用 PostgreSQL 中的 `gda_ontology` 权威存储，同时保留带哈希校验的不可变本体包作为回退。这保证了本体版本和内容可以被审计，而不是每次直接从数据库结构推测。

## 3. 中间的“映射层”最关键

二者真正的连接不是名称相似，而是显式映射：

```text
源表 / 数据模型实体  →  本体类
源字段                →  本体数据属性
外键 / 业务关系       →  本体对象关系
代码表 / 枚举          →  本体值域
几何字段              →  本体空间属性或空间关系
数据血缘              →  本体来源证据
```

例如：

```text
源对象：makani.adac_airport_buildings
        ↓
本体类：Building
        ↓
属性：buildingKey、buildingUse、physicalStatus、geometry
        ↓
关系：locatedIn → Plot
```

但这不是机械的一对一关系：

- 一个本体类可能由多个源表共同实现；
- 一个源表可能只实现某个本体类的一部分；
- 一个字段可能只是技术字段，不应该自动提升为业务属性；
- 外键名称相同，也不代表跨源 JOIN 一定可靠；
- 空间相交可以作为候选关系，但必须记录匹配方法、距离、拓扑规则和置信度。

DMT 当前映射中有 `mapped`、`review_required`、`restricted_review`、`exclude` 等状态。它的 `model_profile` 是 `owl2-rl-bounded-candidate`，明确表示这是由 CDM/LDM/PDM 推导出的候选本体，不代表权威源、业务主键、跨源唯一键和客户审批已经全部确认。

## 4. Agent 查询时两者如何协同

用户问：

> “某个地块有哪些建筑，建筑目前是什么状态？”

本体模型负责：

1. 识别“地块”“建筑”“状态”等业务概念；
2. 找到 `Plot → Building` 的语义关系；
3. 判断“当前状态”应使用哪个属性和有效时间；
4. 选择允许使用的语义视图；
5. 在结果中解释数据来源和可信度。

数据模型负责：

1. 确定实际查询的表或 Gold 视图；
2. 确定字段类型和规范主键；
3. 生成合法的 SQL 或 API 请求；
4. 执行外键 JOIN、空间 JOIN、时间过滤和坐标转换；
5. 处理空值、类型转换、索引和性能问题。

所以本体不会替代 SQL，也不会直接替代 PostGIS 表；它负责约束 SQL 应该表达的业务含义。数据模型也不能独立承担自然语言语义理解。

DMT 为此设计了类似 `gold.vw_plot_building_address` 的语义视图契约，让 Agent 面向稳定的业务粒度查询，而不是直接猜测源表 JOIN。具体见 [DMT 语义视图契约](../customer/dmt_data_model_v1/model/dmt_semantic_view_contracts.md)。

## 5. 对多行业本体的意义

自然资源本体和 DMT 本体应该保持独立：

```text
自然资源数据模型 → 自然资源本体 → 自然资源语义查询
DMT 数据模型       → DMT 本体       → 城市市政语义查询
```

它们可以共享技术基础设施、映射机制、版本治理和 Agent 查询框架，但不应因为都有“建筑”“地块”“道路”等名称，就自动把类合并。

将来如果需要跨行业分析，应建立显式的跨本体对齐关系，例如：

```text
自然资源: 建设用地
        ↔ DMT: Plot
```

这种关系必须有来源、版本、匹配规则和审核状态，而不是依靠名称相似度自动合并。

## 6. 当前系统最重要的边界

本体模型不是数据库 ER 模型的升级版，数据模型也不是本体的低级实现。当前系统采用的是：

- 数据模型作为结构和执行依据；
- 本体模型作为语义和治理依据；
- 映射目录作为两者之间的可审计契约；
- Gold 语义视图作为 Agent 的受控查询入口。

因此，比较合理的后续建设方向是：

1. 每个行业 profile 同时管理本体包和 CDM/LDM/PDM 快照；
2. 支持“从数据模型生成本体候选”；
3. 支持“用本体反向检查数据模型覆盖率”；
4. 对表到类、字段到属性、外键到关系、值域到枚举建立明确映射；
5. 将映射质量、主键确认、SRID 确认和敏感级别作为 Agent 查询的准入条件。

## 一句话概括

> 数据模型告诉 GIS Data Agent “去哪里取、怎么取”；本体模型告诉它“取到的东西是什么、彼此有什么关系、能否可信地解释给用户”。
