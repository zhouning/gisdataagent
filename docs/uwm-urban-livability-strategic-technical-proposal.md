# 面向城市宜居治理的城市世界模型（UWM）战略技术说明

日期：2026-07-05

面向对象：城市规划、住房城乡建设、城市更新、城市体检、生态环境、交通治理、公共服务配置、智慧城市和城市运行管理相关业务负责人；公司管理层；城市空间智能、城市治理数字化和地理信息平台建设相关技术负责人。

## 1. 摘要：UWM 的定位与合作价值

UWM（Urban World Model，城市世界模型）是面向城市宜居治理、环境健康风险、公共服务可达性和空间公平的专业化世界模型。它的目标不是把城市治理简化为一个“宜居性分数”，也不是让人工智能替代规划、建设、环保、交通或公共服务部门的决策职责，而是把城市中的建筑、道路、公共服务、人口、活动、气象、污染、热环境、规划约束和治理动作组织成“可计算、可推演、可审计的城市状态”，支持业务人员识别低宜居区域、解释形成机制、比较干预方案、评估公平性影响并生成证据链。

可以用一句话概括：

> UWM 是面向城市宜居治理和城市更新决策的智能推演与证据审计引擎，用于帮助城市管理者更系统地理解城市状态、更早发现宜居风险、更稳健比较干预方案、更清楚说明依据和不确定性。

UWM 的基本原则是：

- 人本导向：宜居性不只是建筑、道路和设施数量，而是居民在环境健康、服务可达、空间公平和生活便利方面的综合感受与风险状态；
- 状态统一：把建筑、道路、POI、AOI、人口、通勤、遥感、气象、污染、热环境和规划约束转化为统一的城市状态；
- 动作条件推演：不只回答“哪里问题严重”，还回答“如果采取某类城市干预，未来状态会怎样变化”；
- 证据分级：真实观测、公开代理、拟合代理、半合成数据和合成数据必须分级标注，不能混用为同等证据；
- 模型辅助：模型用于诊断、推演、方案搜索和证据组织，不直接生成行政决定或政策结论；
- 公平约束：不能只追求平均宜居性提高，还必须说明低宜居区域、脆弱人群和高暴露群体是否真正受益；
- 全程留痕：数据来源、处理过程、模型输入、动作序列、推演轨迹、评价指标、证据等级和人工复核记录必须可追溯；
- 分级验证：工程闭环、公开数据验证、历史回放、真实观测 holdout、政策 outcome 验证必须分级推进，不能把演示结果包装成生产结论。

当前 UWM 已经不是一份纯概念方案。`gisdataagent` 项目中已经形成 UWM 数据基础、MMFE 状态输入、renderer、scene state、simulator、evidence-gated planner、Graph-MDP、离线 value/world-model policy、learned rollout planner 和评估门控等可运行工程骨架。已有材料显示，UWM 在 OpenAQ 600 条真实小时观测 temporal holdout 上的 online temporal state update 显著优于传统静态 baseline suite；在重庆行政单元 proxy 场景中，已完成 1,017 个乡镇/街道行政单元、2,847 条行政邻接边、36 个宜居候选单元、355 条 simulator replay transitions 的模型式规划闭环。

但 UWM 仍必须保持边界：当前还不能宣称 UWM planner 已经在真实政策干预 outcome 上优于传统方法。现阶段最稳妥的定位是：

1. UWM 已经具备可运行的城市世界模型工程链条；
2. UWM 已经在状态预测层和 known-effect simulator/proxy 场景中形成验证证据；
3. UWM 仍需要接入真实政策干预 outcome、站点校准的场景一致空气质量观测、权威人口和出行数据、因果识别证据，才能进入更高等级的政策效果证明；
4. UWM 适合以城市体检、城市更新、气候健康风险、公共服务补短板和空间公平治理为切入点，与城市业务部门开展分级试点。

本说明书的核心目的不是宣称 UWM 已经完成，而是说明：

1. 城市宜居治理面临的问题真实存在，且传统静态指标体系难以充分支撑动态干预决策；
2. UWM 的技术路线已经从概念进入可实现、可验证、可审计的工程路径；
3. UWM 不替代城市治理部门的职责，而是增强状态诊断、机制解释、干预推演、方案比选和证据留痕能力；
4. 只有接入真实权威数据和真实业务流程，UWM 才能完成从研发验证到生产验证的关键跃迁。

## 2. 当前城市宜居治理面临的核心问题

近年来，各地城市治理已经积累了大量数据和系统，包括城市体检、城市更新、CIM、城市运行平台、实景三维、时空大数据平台、交通运行监测、生态环境监测、公共服务设施库、人口和活动数据、遥感影像、建筑轮廓、POI/AOI、道路网络和各类专项规划。

这些系统构成了城市治理数字化的基础，但在面向“宜居、韧性、低碳、健康、公平”的更高目标时，仍面临几个突出问题。

### 2.1 数据很多，但还没有统一转化为“城市状态”

城市数据往往分散在不同部门、不同平台和不同专业系统中。规划部门掌握用地和规划约束，住建部门掌握城市更新和建设项目，生态环境部门掌握空气质量和污染排放，交通部门掌握道路和运行状态，公共服务部门掌握教育、医疗、养老、商业和文体设施，统计或运营商数据反映人口和活动，遥感数据反映地表覆盖、热环境和建设强度。

传统 GIS 和城市运行平台能够展示、查询、叠加和统计这些数据，但对“当前城市宜居状态是什么”这一问题，还缺少统一的可计算表达。

例如，一个街道或社区的宜居状态并不只取决于是否有学校、医院和公园。它还涉及：

- 居民是否暴露在高温、高污染或高交通压力环境中；
- 公共服务是否真正可达，而不是只在行政区内存在；
- 脆弱人群、老年人、低收入群体或高暴露群体是否受益；
- 建筑密度、道路结构、绿地水体和活动强度是否形成不利耦合；
- 规划约束、用地条件和项目条件是否允许采取干预；
- 数据来源是否可靠，时间是否一致，空间尺度是否可比。

如果这些信息仍停留在分散图层、报表和仪表盘中，系统就很难回答：

- 哪些空间单元处于低宜居性陷阱？
- 低宜居性到底由热暴露、污染暴露、服务不足、人口脆弱性还是多因素耦合造成？
- 哪些区域虽然平均分不低，但高暴露群体或弱势人群风险更高？
- 哪些干预动作在当前空间条件和规划约束下可实施？
- 如果采取不同干预方案，未来状态会怎样变化？

UWM 要解决的第一件事，就是把分散城市数据组织成可计算、可推演、可审计的城市状态。

### 2.2 宜居性评价容易停留在静态加权分数

传统宜居性评价常见路径是：

```text
指标选取 -> 标准化 -> 加权叠加 -> 空间分区 -> 排名解释
```

这类方法对快速识别问题区域有价值，但存在明显局限：

- 指标权重往往难以解释，容易变成“分数工程”；
- 输出多是静态排名，难以说明干预后会怎样；
- 对热暴露、污染暴露、交通压力、人口脆弱性和公共服务之间的耦合关系表达不足；
- 难以处理空间溢出，例如某区域增绿对周边热风险和活动舒适度的影响；
- 难以说明低宜居区域和脆弱人群是否真正受益；
- 难以区分真实观测、公开代理、拟合代理和合成数据的证据等级。

UWM 不是取消传统宜居性评价，而是在传统评价之上增加动态能力。它不只输出“哪里宜居性低”，还输出：

- 为什么低；
- 应该采取哪类干预；
- 干预后哪些指标会改善；
- 改善是否具有空间公平性；
- 结论有多少证据支持；
- 哪些结论只能作为探索性情景。

### 2.3 环境健康、公共服务和空间公平常被割裂处理

城市宜居性并不是单一专业问题。热环境、空气污染、道路交通、建筑形态、绿地水体、公共服务、人口脆弱性和社会公平共同影响居民生活质量。

在实际工作中，这些主题经常由不同部门、不同系统和不同指标体系分别处理：

- 热环境和污染暴露属于生态环境、气象、遥感或城市气候分析；
- 公共服务设施属于住建、规划、教育、医疗、民政、文体等部门；
- 道路交通和出行可达性属于交通部门；
- 人口脆弱性和社会公平属于统计、民政、社区治理和城市体检工作；
- 城市更新和项目实施属于住建、规划和属地政府。

如果缺少统一状态和统一证据链，一个区域可能在某个指标上表现较好，但在综合宜居性上仍然存在问题。例如，某片区服务设施数量充足，但老年人口高、热风险高、慢行可达性差；另一个片区绿地覆盖较好，但交通污染暴露高、公共服务不足、低收入群体更集中。

UWM 的价值在于把这些因素放入同一个城市状态和同一个干预推演框架中，帮助业务人员从“单指标治理”走向“多目标协同治理”。

### 2.4 能看到现状，但难以系统推演“如果这样做会怎样”

城市治理经常需要回答行动后果问题：

- 如果在某些街道增加绿地、树冠或蓝绿基础设施，热风险和宜居性是否改善？
- 如果在道路走廊采取交通减排或低排放管控，污染暴露是否下降？
- 如果补充社区公共服务设施，哪些低宜居区域会真正受益？
- 如果对高热风险建筑群采取冷屋顶或建筑降温改造，脆弱人群暴露是否降低？
- 如果多个方案都可实施，哪个方案的综合收益更高、风险更低、证据更充分？

传统 GIS 擅长看清楚“现在是什么”，传统评价模型可以给出“现状分数”，但对“行动后的未来状态和风险变化”支持不足。UWM 的核心价值正在这里：它以“当前城市状态 + 干预动作 + 外部情景 + 规划约束 + 证据等级”为输入，推演未来状态、指标变化、空间溢出、公平性影响、不确定性和复核需求。

### 2.5 人工智能能回答问题，但不能直接成为城市治理依据

当前大模型和智能体技术发展很快，已经可以帮助业务人员查询资料、生成报告、调用工具和组织分析流程。但城市治理不能直接依赖“模型说了什么”。原因很明确：

- 城市规划和建设管理必须遵守法定规划、技术标准和审批程序；
- 环境治理和公共服务配置需要真实数据和责任边界；
- 政策效果判断必须有观测证据、历史回放或因果识别支撑；
- 城市更新和公共资源配置涉及公平性和社会影响，不能由黑箱模型直接决定；
- 涉及人口、出行、健康和行为数据时必须满足数据安全、隐私保护和授权要求。

因此，城市行业真正需要的不是一个会聊天的人工智能，而是一个能够与城市数据、空间关系、规划约束、环境健康机制、公共服务可达性、空间公平和人工复核机制结合的智能治理引擎。

UWM 的设计正是基于这一判断：人工智能用于辅助状态构建、机制解释、情景推演、方案搜索和证据组织；结论是否能进入业务使用，必须由数据权威性、模型验证、证据门控、专家复核和责任主体共同决定。

## 3. UWM 是什么：第一性原理与边界

### 3.1 UWM 的第一性原理

UWM 的第一性原理可以用三句话说明。

第一，城市治理的对象本质上是多尺度城市状态。

城市不是单一图层，也不是一张静态地图。城市状态同时包括建筑、道路、街区、社区、行政单元、公共服务设施、绿地水体、人口分布、通勤活动、热环境、空气污染、气象条件、用地约束和项目条件。这些对象既有空间位置，也有时间变化、功能联系、网络关系和证据质量。

第二，城市治理和城市更新行为本质上是对城市状态的干预。

增绿、交通减排、公共服务补点、冷屋顶改造、慢行网络优化、城市更新、街区微改造、公共空间提升、污染源治理和规划实施，都会改变或影响城市状态、居民暴露、服务可达性和公平性。

第三，好的城市智能工具必须能够预测干预后果，并说明证据、边界和不确定性。

如果一个系统只能展示现状，它只是静态 GIS 或 dashboard；如果一个系统只能给出模型分数，却不能说明依据和边界，它不能进入严肃治理场景；只有把状态、动作、推演、证据、约束、公平和复核组织在一起，才有可能形成可信的城市世界模型。

因此，UWM 的基本形式可以表达为：

> 当前城市状态 + 干预动作 + 外部情景 + 规划约束 + 证据等级 -> 未来城市状态、宜居性变化、环境健康风险、公平性影响、不确定性、复核需求、证据链

更技术化地说，UWM 关注的是：

```text
P(next_state, livability_state, exposure_state, equity_state |
  current_state, action, scenario, urban_graph, constraints, evidence)
```

对业务人员来说，不需要强调公式。核心意思是：UWM 不只看现在，而是推演“如果采取某种城市治理或更新行动，未来可能怎样，并且为什么这样判断”。

### 3.2 UWM 不是什么

为了避免误解，需要明确 UWM 的边界。

UWM 不是通用大模型。

它不是一个只靠语言理解回答问题的系统。它需要真实城市数据、空间对象、网络关系、环境观测、公共服务设施、人口活动、规划约束和验证记录支撑。大模型可以作为交互入口和任务编排助手，但不能替代 UWM 的城市状态、动作、推演和证据门控。

UWM 不是普通宜居性指数。

传统宜居性指数通常是静态指标加权。UWM 必须包含状态、动作、轨迹、推演、证据和不确定性。如果一个系统只输出宜居性排名图，而不能推演干预后果，它不能称为完整 UWM。

UWM 不是地图展示或城市驾驶舱。

UWM 可以为地图和驾驶舱提供智能分析结果，但它的核心不在可视化界面，而在城市状态构建、动作条件模拟、方案搜索和证据审计。前端展示只是结果表达，不是 UWM 本体。

UWM 不是传统数字孪生的简单换名。

数字孪生通常强调对象映射、可视化、运行监测和三维表达。UWM 更强调行动条件推演、反事实比较、空间公平、因果证据和验证阶梯。它可以成为城市数字孪生或 CIM 平台中的智能推演核心，但不等同于三维展示系统。

UWM 不是自动规划或自动审批系统。

UWM 输出应定位为辅助研判、风险预警、方案比较和证据组织。规划方案、建设计划、交通治理、生态环境治理和公共服务配置仍应由有权部门和责任人员依据法律法规、技术标准、财政预算、公众参与和专家复核作出。

### 3.3 UWM 与当前“世界模型”热潮的关系

“世界模型”这个概念正在变热，确实存在泛化和炒作风险。很多场景把它理解为“能模拟世界的一切模型”，这并不严谨。

UWM 与通用世界模型的共同点是：都关心状态、动作和未来结果。

但 UWM 的不同之处在于：

- UWM 的世界是城市治理世界，不是抽象物理世界；
- UWM 的对象不是视频帧或像素，而是建筑、道路、街区、设施、人群、活动、环境暴露和规划约束；
- UWM 的动作不是机器人控制，而是城市更新、增绿、交通减排、公共服务补点、冷屋顶改造、慢行改善等治理行动；
- UWM 的目标不是生成逼真场景，而是识别风险、解释机制、比较方案、说明证据和支持复核；
- UWM 的可信度不是来自模型规模，而是来自数据来源、时空一致性、历史回放、真实观测、因果校准、证据门控和人工复核。

因此，更准确的说法是：

> UWM 是世界模型思想在城市宜居治理领域的专业化落地。它吸收“状态-动作-未来”的基本思想，但把模型边界严格限定在城市状态诊断、干预推演、空间公平评估和治理证据审计场景中。

## 4. UWM 与传统 GIS、城市体检、数字孪生和宜居性评价的区别

| 对比对象 | 主要特点 | 与 UWM 的关系 | UWM 的差异 |
|---|---|---|---|
| 传统 GIS | 图层管理、空间查询、叠加分析、制图表达 | UWM 必须建立在 GIS 能力之上 | UWM 进一步把图层转化为可推演城市状态 |
| 城市体检 | 指标监测、问题识别、年度评估、整改建议 | UWM 可作为城市体检的动态推演和证据增强能力 | UWM 不只评估现状，还推演治理动作后果 |
| 城市运行平台 | 运行监测、事件处置、指标看板、联动调度 | UWM 可为平台提供预测和方案比选能力 | UWM 强调状态转移、情景模拟和证据门控 |
| CIM / 数字孪生 | 城市对象映射、三维表达、监测仿真 | UWM 可作为其中的智能推演核心 | UWM 更强调干预动作、反事实比较、公平性和验证阶梯 |
| 宜居性评价 | 指标体系、加权叠加、空间排名 | UWM 需要吸收其指标基础 | UWM 把静态评价升级为动态干预推演 |
| 交通/环境专项模型 | 针对单一系统进行预测或评估 | 可作为 UWM 的子模型或证据来源 | UWM 关注多系统耦合和跨部门方案比较 |
| 通用大模型/智能体 | 语言理解、问答、任务编排、工具调用 | 可作为 UWM 的交互入口 | UWM 的可信性来自城市状态、规则、观测和验证，不来自语言生成 |

这个区别非常重要。UWM 不是要推翻现有 GIS、城市体检、CIM、数字孪生或城市运行平台，而是要在这些基础之上增加一类新的能力：**可推演、可反事实、可规划、可审计的城市宜居治理智能能力**。

## 5. UWM 能解决的城市业务问题

### 5.1 城市宜居性诊断：从静态排名到机制解释

城市宜居性诊断不能停留在“某区域分数低”。业务人员更需要知道：

- 低宜居性由什么机制造成；
- 是热风险、污染暴露、服务不足、交通压力、人口脆弱性还是多因素耦合；
- 哪些问题可以通过城市更新或公共服务补短板缓解；
- 哪些问题需要生态环境、交通、住建、规划和属地政府联合治理；
- 哪些结论证据充分，哪些只是代理指标提示。

UWM 可以把低宜居区域识别与机制解释绑定起来，形成“问题单元-问题机制-可选动作-证据等级”的治理视图。

### 5.2 气候健康风险：从热力图到人群暴露和治理动作

高温热暴露、城市热岛、静稳天气和空气污染会直接影响居民健康风险。传统热力图或污染图能展示空间分布，但往往难以回答治理动作问题。

UWM 可以支持：

- 识别高热暴露、高污染暴露和高脆弱性叠加区域；
- 区分环境风险高但人口暴露低、人口暴露高但环境指标中等、以及多风险耦合区域；
- 推演增绿、冷屋顶、交通减排等动作对热风险和污染暴露的潜在影响；
- 评估风险降低是否真正惠及脆弱人群；
- 为气候适应、健康城市和韧性城市建设提供证据。

### 5.3 公共服务可达性：从设施数量到真实服务缺口

公共服务配置不能只看设施数量和行政区覆盖。居民实际能否到达服务设施，取决于空间距离、路网连通、慢行条件、交通成本、服务容量、人口结构和活动路径。

UWM 可以辅助：

- 识别医疗、教育、养老、商业、公园、文体和社区服务的空间缺口；
- 判断缺口是否与高脆弱人群、高热风险或高污染暴露叠加；
- 对公共服务补点方案进行情景比较；
- 评估服务补点对周边区域和低宜居区域的溢出改善；
- 形成“补哪里、补什么、为什么补、证据到什么等级”的方案包。

### 5.4 空间公平和环境正义：从平均改善到“谁受益”

城市治理不能只看平均分。一个方案可能提高全市平均宜居性，却没有改善低宜居区域和高暴露人群的处境。UWM 必须回答：

- 低宜居区域是否得到优先改善；
- 脆弱人群是否从干预中获益；
- 高污染、高热风险、高服务缺口区域是否被覆盖；
- 改善是否集中在原本条件较好的区域；
- 是否存在风险转移或空间不公平。

这使 UWM 能够支持城市更新、公共服务补短板、气候适应和环境治理中的公平性评估。

### 5.5 城市更新和微干预：从项目清单到多步优化方案

城市更新往往涉及多个小尺度项目和多类干预动作。单个项目可能收益有限，但组合起来可能形成更明显的空间改善。

UWM 可以支持：

- 识别最应治理的街道、社区、街区或网格；
- 判断每个空间单元适合增绿、交通减排、服务补点、冷屋顶改造还是慢行改善；
- 搜索多步 action sequence，而不是只给单步建议；
- 对多种预算和约束情景进行方案比较；
- 输出干预前后热风险、污染暴露、服务可达性、公平性和综合宜居性的变化。

### 5.6 跨部门协同治理：从数据汇聚到证据协同

宜居治理天然跨部门。一个低宜居区域可能同时涉及住建更新、道路交通、生态环境、公共服务、属地治理和规划约束。

UWM 可以把跨部门数据组织到统一状态中，并把模型输出拆解为不同部门可理解的证据：

- 规划部门关注空间约束、用地条件和实施边界；
- 住建部门关注城市更新项目和建设可行性；
- 生态环境部门关注污染暴露和治理效果；
- 交通部门关注道路活动、慢行网络和交通减排；
- 公共服务部门关注设施缺口和服务半径；
- 属地政府关注社区需求、风险点和项目落地。

UWM 的价值不只是“算一个结果”，而是形成跨部门可沟通、可复核、可追溯的治理证据。

### 5.7 证据审计：从模型输出到可追溯治理依据

城市治理中的模型输出必须能说明依据和边界。UWM 可以将数据来源、处理步骤、模型版本、动作序列、推演轨迹、指标变化、不确定性和人工复核记录纳入统一证据链。

这使业务人员能够回答：

- 依据哪些数据；
- 数据是什么时间、什么空间尺度、什么来源；
- 哪些指标是真实观测，哪些是公开代理或拟合代理；
- 哪些结果来自 simulator replay，哪些来自真实 holdout；
- 哪些结论可以用于内部研判，哪些不能用于对外政策主张；
- 哪些结果需要人工复核或补充数据。

## 6. UWM 的总体技术架构：从城市数据到城市世界模型

UWM 可以分为八个层次：城市数据基础、语义融合与数据契约、renderer、城市状态编码、simulator、planner、因果证据门控、报告与业务闭环。

### 6.1 城市数据基础与 manifest

UWM 首先需要一套可审计的城市数据基础。数据不应以“有一个文件”或“能在地图上显示”为准，而应进入统一 manifest，记录：

- 数据名称和数据角色；
- 来源、获取日期和许可约束；
- 空间范围、时间范围和坐标系统；
- 数据类型：真实数据、公开代理、拟合代理、受限预期、半合成或合成；
- 是否允许用于生产结论；
- 质量问题和已知缺口；
- 下游用途和 claim boundary。

当前 `gisdataagent` 项目中的 UWM 数据基础已经登记 61 行 manifest，其中包括本地真实资产、公开代理、拟合代理、半合成数据和合成脚手架。这个分级非常重要，因为 UWM 的可信度不只取决于模型，也取决于数据是否能支持相应等级的结论。

### 6.2 MMFE 与语义融合：数据进入 UWM 的前级

城市数据来源复杂、字段口径不一、空间尺度不同、时间窗口不同。MMFE（多模态地理空间语义融合能力）在 UWM 中的角色不是旁路工具，而是数据融合和语义对齐前级。

UWM 需要通过类似 `mmfe.uwm_state_input.v1` 的契约消费 MMFE 产出的角色绑定、字段绑定、质量 sidecar 和语义关系。换句话说，UWM 不应该直接在 simulator 中读取散乱原始文件，而应该先形成可审计、可复现、可解释的标准化城市观测输入。

### 6.3 Renderer：城市观测算子

UWM 中的 renderer 不是前端地图渲染器，而是城市观测算子：

```text
raw urban data / MMFE product -> UwmCanonicalObservation.v1
```

它把真实世界中的多源城市数据转成 simulator 可消费的城市观测状态。Renderer 必须同时处理对象和场：

- 对象：建筑、道路、POI、AOI、公共服务设施、街区、行政边界；
- 场：热环境、NDVI/NDBI、PM2.5、NO2、O3、人口栅格、气象栅格、遥感表征。

Renderer 输出不应是图片，而应包含：

- spatial units；
- object layers；
- raster features；
- graph edges；
- temporal index；
- action masks；
- quality flags；
- synthetic/proxy flags；
- provenance；
- claim boundary；
- renderer trace。

只有这样，后续 simulator 和 planner 才能知道自己使用了什么数据、哪些数据可靠、哪些数据只能作为代理、哪些空间单元允许采取哪些动作。

### 6.4 城市状态编码：对象-场-图的统一表达

城市状态既不是纯表格，也不是纯栅格。UWM 需要同时表达：

- 建筑和设施等对象；
- 热环境、污染、人口等连续场；
- 道路、邻接、通勤、功能相似和环境传播等图关系；
- 时间窗口和外部情景。

因此，UWM 的状态编码应体现城市复杂系统的特点：

```text
城市观测 O_t
-> 城市状态 z_t
-> 城市图 G
-> 干预动作 a_t
-> 未来状态 z_t+1
```

如果只把所有指标压成一个扁平表格，UWM 就无法表达空间邻接、道路连通、服务可达、污染传播和干预溢出。

### 6.5 Simulator：动作条件城市动力学模型

Simulator 是 UWM 的 transition model：

```text
P(z_t+1, y_t+k | z_t, a_t, e_t, G)
```

它不是“预测未来宜居性分数”，而是模拟城市状态在干预动作和外部情景下如何变化。

UWM 中的动作应对应真实城市治理或规划干预，例如：

- `increase_green_infrastructure`：增绿、树冠、蓝绿基础设施；
- `traffic_emission_control`：交通减排、低排放区、道路活动管控；
- `add_community_service`：公共服务补点；
- `cool_roof / retrofit`：冷屋顶、建筑降温改造；
- `walkability_improvement`：慢行网络和街道空间改善。

Simulator 输出不应只有一个综合分，而应包括：

- heat risk delta；
- air pollution exposure delta；
- service accessibility delta；
- equity delta；
- livability delta；
- spatial spillover；
- uncertainty interval；
- negative control；
- rollout trace；
- evidence grade；
- claim boundary。

### 6.6 Planner：证据门控的城市干预搜索器

Planner 的职责不是自己生成收益，也不是绕过 simulator 直接对当前分数排序。合格的 UWM planner 必须消费 simulator trace，并在约束和证据门控下搜索干预方案。

Planner 要回答的问题是：

```text
在预算、空间、规划、证据和公平约束下，
选择哪些城市干预动作，使未来宜居性、环境健康和空间公平改善最大，
并且风险和不确定性可接受。
```

UWM planner 应输出的是方案包，而不是一句建议。方案包至少包括：

- 推荐动作序列；
- 作用空间单元；
- 预计指标变化；
- 受益人群和公平性结果；
- 证据等级；
- 不确定性；
- 需要人工复核的事项；
- 不建议采用的备选方案及原因。

### 6.7 因果证据门控：不把相关性当政策效果

城市干预效果不能直接从相关性推出。某个区域污染高、服务少、宜居性低，并不自动说明某个干预动作一定有效。UWM 必须将反事实推演和证据等级分开。

证据门控应至少区分：

- 工程可运行；
- proxy 场景可解释；
- 历史观测状态预测有效；
- 历史回放有效；
- 真实观测 holdout 有效；
- 准实验或因果识别支持；
- 真实政策 outcome 支持。

当前 UWM 已经有状态预测层和 known-effect simulator/proxy 场景的验证，但真实政策 outcome 和因果识别仍是下一阶段重点。

### 6.8 报告与业务闭环

UWM 的最终结果应服务业务闭环，而不是停留在模型文件。建议输出四类成果：

1. 城市状态诊断报告：说明低宜居区域、机制和证据；
2. 干预方案包：说明动作序列、预期改善、约束和不确定性；
3. 证据审计包：说明数据来源、模型过程、验证结果和 claim boundary；
4. 复核任务清单：列出需要业务专家、数据管理员或部门负责人确认的问题。

### 7.4 Graph-MDP 与模型式规划验证

当前材料记录，UWM 已经完成 admin spatial adjacency Graph-MDP v0：

这些结果可以说明：

- UWM 已经具备 Graph-MDP / model-based rollout search scaffold；

- 这仍是 simulator replay 和 proxy target 场景；
- 行政空间邻接图不是道路网络、交通流、OD 或 travel-time accessibility；
- 当前不是完整在线 PPO/DRL；
- 不能宣称 UWM 已经在真实政策 outcome 上优于传统方法。

### 7.5 OpenAQ temporal holdout 的状态预测证据

当前最强的事实性证明来自 OpenAQ temporal benchmark：

```text
observations = 600
pollutants = 6
holdout_points = 180
dynamic wins vs static_train_mean = 150/180
sign test vs static_train_mean p = 3.17e-23
sign test vs static_last_train_observation p = 7.02e-28
PM2.5 best static baseline MAE = 9.466667
PM2.5 dynamic MAE = 2.4
PM2.5 sign test vs best static p = 2.82e-6
ordered-vs-shuffled temporal control = passed on 6/6 pollutants
```

可以稳妥声明：

> UWM online temporal state update 在真实 OpenAQ 时间序列 holdout 上，显著优于传统静态 baseline suite，并通过时间顺序负控。

不可声明：

> UWM planner 已经在真实政策 outcome 上优于传统方法。

这一区分对外沟通非常重要。状态预测有效是重要进展，但不等同于政策干预效果已经被真实验证。

### 7.6 仍需明确的边界

当前 UWM 的边界包括：

- 空气污染 2024 场景仍缺 station-calibrated observed holdout；
- TAP 数据处于 restricted_expected / registration pending 状态，未下载前不能作为可用证据；
- NOAA ISD 已补入江北站 2024-07 观测，但仍不是全城格网或面状气象校准；
- 人口脆弱性仍缺乡镇/街道级权威人口、脆弱人群细分和 2024 场景人口；
- 服务可达性仍缺全市完整 POI、权威服务目录和 network travel-time surface；
- mobility / travel time / OD 仍缺格网几何字典、真实出行时间、交通流和网络阻抗；
- 当前 planner 优势主要来自 known-effect simulator 和 proxy target，不是 observed intervention outcome；
- 行政边界许可、官方年代和 crosswalk 仍需核验；
- 真实因果识别和政策效果验证仍未完成。

这些边界不是缺点，而是 UWM 走向可信生产能力必须明确标注的证据纪律。

## 8. 真实落地还需要的条件和试点建议

### 8.1 需要的数据条件

面向真实城市业务试点，建议至少准备以下数据：

- 权威行政边界、街道社区边界、网格或街区单元；
- 建筑轮廓、高度、年代、用途或建设强度；
- 道路网络、慢行网络、公交站点、轨道站点和出行阻抗；
- 公共服务设施目录，包括医疗、教育、养老、文体、商业、公园和社区服务；
- 人口总量、年龄结构、脆弱人群、居住分布和活动分布；
- 气象、热环境、遥感植被、水体和地表覆盖；
- 空气质量站点、污染代理或排放相关数据；
- 城市更新项目、公共服务补点计划、增绿计划、交通治理项目等真实干预记录；
- 规划约束、用地条件、项目实施条件和预算约束；
- 历史监测和政策 outcome，用于回放和验证。

如果某些数据暂时缺失，可以使用公开代理或拟合代理进行工程验证，但必须明确降级，不得作为真实政策效果依据。

### 8.2 需要的业务条件

UWM 试点需要业务部门参与定义：

- 哪些问题属于试点范围；
- 哪些空间单元作为治理单元；
- 哪些指标构成宜居性目标；
- 哪些干预动作真实可实施；
- 哪些约束是硬约束；
- 哪些输出可以作为内部研判，哪些可以进入业务流程；
- 哪些结论必须人工复核；
- 谁负责数据确认、模型复核和业务解释。

没有业务动作和复核机制，UWM 容易退化为指标展示；没有数据和证据门控，UWM 容易退化为概念演示。

### 8.3 需要的验证条件

建议采用分级验证路线：

第一层：工程验证。

确认数据能够进入 manifest，renderer 能输出 canonical observation，simulator 能生成 rollout trace，planner 能输出 plan package，结果可复现。

第二层：状态预测验证。

使用真实观测 holdout 验证 UWM 对污染、热环境、服务可达性或人口活动等状态变量的预测能力。

第三层：历史回放验证。

使用历史城市更新、增绿、交通治理、公共服务补点或环境治理案例，回放干预前后变化。

第四层：政策 outcome 验证。

使用真实或准真实政策干预 outcome，比较 UWM 方案与静态启发式、人工经验方案或传统模型方案的差异。

第五层：生产监控验证。

在试点业务流程中持续记录模型建议、人工复核、实际实施和后续效果，形成闭环评估。

### 8.4 需要的部署条件

UWM 涉及城市空间数据、人口活动数据、可能的运营商或敏感行业数据，应优先支持：

- 本地化部署；
- 专有云或政务云部署；
- 内网运行；
- 数据脱敏和分级授权；
- 模型和数据操作审计；
- 人工复核权限控制；
- 对外输出前的 claim boundary 检查。

UWM 不应要求城市敏感数据出域，也不应将未经授权的人口、通勤、健康或行为数据上传到外部服务。

## 9. 风险控制：不替代治理职责、不越权决策、证据门控、人工复核

### 9.1 不替代城市治理部门职责

UWM 的输出是辅助研判和方案比较，不是行政决定。规划、建设、交通、生态环境、公共服务和城市更新相关结论仍应由有权部门依法依规作出。

### 9.2 不越权生成政策结论

UWM 可以说明“在当前数据和模型假设下，某类干预可能带来某种改善”，但不能越权表述为“系统已经决定应该实施某项目”或“模型证明某政策必然有效”。

尤其在当前阶段，不能宣称：

- UWM planner 已经在真实政策 outcome 上优于传统方法；
- proxy target 可以代表真实健康或宜居 outcome；
- 行政空间邻接图可以代表道路网络、交通流或出行时间；
- 合成或半合成数据可以替代真实观测；
- 大模型回答可以替代业务部门审查。

### 9.3 证据不足时必须降级

当数据来源、时间窗口、空间尺度、代理变量、模型验证或因果证据不足时，UWM 必须自动降级输出：

- 从政策结论降级为内部研判；
- 从内部研判降级为探索性情景；
- 从探索性情景降级为数据补充需求；
- 从自动建议降级为人工复核任务。

### 9.4 公平性必须显式检查

宜居治理不能只优化平均指标。UWM 必须显式检查：

- 低宜居区域是否改善；
- 高暴露人群是否改善；
- 脆弱人群是否改善；
- 是否出现风险转移；
- 是否只改善了原本条件较好的区域。

如果平均宜居性提高但公平性恶化，方案不应被视为高质量方案。

### 9.5 全程留痕

UWM 的每次分析都应记录：

- 数据版本；
- 规则和约束版本；
- 模型版本；
- 参数和情景；
- 动作集合；
- rollout trace；
- planner 输出；
- evidence gate 结果；
- 人工复核意见；
- 对外表述边界。

这既是技术要求，也是城市治理中责任可追溯的要求。

## 10. 未来发展前景与战略价值

### 10.1 从静态城市体检走向可推演城市体检

城市体检已经为城市问题识别提供了重要抓手，但很多工作仍停留在年度指标评价和问题清单。UWM 可以把城市体检推进到“问题识别 + 机制解释 + 干预推演 + 证据复核”的新阶段。

### 10.2 从平均宜居性走向公平导向的治理优化

传统指标体系容易追求平均改善。UWM 可以把低宜居区域、脆弱人群和高暴露群体纳入目标函数，使城市治理更关注“谁受益、谁仍然被遗漏”。

### 10.3 从城市数字孪生展示走向智能推演核心

许多城市数字孪生平台重展示、重接入、重驾驶舱，但缺少可验证的行动后果推演能力。UWM 可以作为数字孪生、CIM 和城市运行平台之上的智能推演核心。

### 10.4 从单点项目交付走向可复用城市智能产品

UWM 的核心不是某个城市的一次性报告，而是一套可复用能力：

- 数据 manifest；
- 城市状态契约；
- renderer；
- simulator；
- planner；
- evidence gate；
- 评估基准；
- 证据审计包。

这些能力可以在不同城市、不同区县、不同业务主题中复用和扩展。

### 10.5 可扩展到其它城市治理主题

UWM 首期可聚焦城市宜居性，但能力可扩展到：

- 城市更新优先区识别；
- 气候适应和热风险治理；
- 空气污染暴露和健康风险；
- 15 分钟生活圈与公共服务补短板；
- 老龄友好和儿童友好城市；
- 低碳交通和慢行改善；
- 韧性城市和灾害风险；
- 城市精细化治理和社区治理。

## 11. 建议的试点路线

### 11.1 第一阶段：数据和业务边界试点

目标是建立可信输入，而不是急于宣传模型效果。

建议任务：

- 选择一个城市或区县作为试点；
- 明确空间单元，例如街道、社区、网格、街区或 250m/500m 网格；
- 建立数据 manifest；
- 明确真实数据、公开代理、拟合代理、半合成和合成数据边界；
- 确定宜居性指标体系和业务动作集合；
- 确定哪些输出可以用于内部研判，哪些必须人工复核。

阶段成果：

- UWM 数据清单；
- 城市状态契约；
- 指标和动作字典；
- 数据质量和缺口报告；
- 试点区低宜居性初步诊断。

### 11.2 第二阶段：状态构建和传统 baseline

目标是证明 UWM 能形成比传统静态评价更可解释的城市状态。

建议任务：

- 构建 canonical observation；
- 形成传统宜居性 baseline；
- 形成 UWM 状态表达；
- 对比传统静态评价和 UWM 状态诊断的差异；
- 标注低宜居区域、机制解释和证据等级；
- 建立真实观测 holdout 或历史状态验证。

阶段成果：

- 城市状态图谱；
- 传统 baseline 报告；
- UWM 机制诊断报告；
- 状态预测验证报告。

### 11.3 第三阶段：动作条件推演和方案比选

目标是验证 UWM 能回答“如果这样做会怎样”。

建议任务：

- 选定可实施动作，例如增绿、交通减排、服务补点、冷屋顶改造；
- 建立 action mask 和约束；
- 使用 simulator 进行单步和多步 rollout；
- 比较 UWM model-based planner 与静态启发式方案；
- 输出方案包和证据等级；
- 组织业务专家复核。

阶段成果：

- 干预方案包；
- 干预前后指标对比；
- 公平性影响报告；
- 不确定性和复核清单；
- known-effect 或历史回放 benchmark。

### 11.4 第四阶段：真实政策 outcome 验证

目标是从工程和 proxy 验证推进到更高等级的业务验证。

建议任务：

- 收集真实城市更新、增绿、交通治理或公共服务补点案例；
- 建立干预前后状态和 outcome；
- 做历史回放、负控和因果门控；
- 比较 UWM 方案、人工经验方案和传统静态方案；
- 明确哪些结论可以提升为政策效果证据，哪些仍需降级。

阶段成果：

- 真实政策 outcome 验证报告；
- 因果证据审计；
- 生产试点建议；
- 对外可声明边界。

## 12. 对城市业务部门合作的建议

### 12.1 建议选择的试点方向

建议优先选择以下方向之一：

1. 城市宜居性和低宜居区域识别；
2. 城市体检问题区的机制解释和整改方案推演；
3. 高温热风险和脆弱人群暴露治理；
4. 空气污染暴露和交通减排协同治理；
5. 15 分钟生活圈和公共服务补短板；
6. 城市更新片区的多方案比选；
7. 老旧小区、街区微更新和公共空间提升；
8. 公平导向的公共资源配置。

这些方向都具有明确业务价值，也能较好体现 UWM 的状态、动作、推演和证据能力。

### 12.2 建议建立联合工作机制

建议建立联合工作组，包括：

- 业务牵头部门；
- 数据管理部门；
- 规划、住建、生态环境、交通、公共服务相关专业人员；
- GIS 和数据工程团队；
- 模型和算法团队；
- 信息安全和数据合规人员；
- 试点区县或街道代表。

联合工作组应共同确认：

- 数据授权和使用边界；
- 试点问题和指标体系；
- 可实施动作和约束；
- 验证方案；
- 人工复核流程；
- 对外发布口径。

### 12.3 建议采用“辅助决策”而非“自动决策”定位

对外建议使用“城市宜居治理辅助研判”“城市更新方案推演”“城市体检智能增强”“证据门控的城市干预方案比选”等表述，避免使用“自动决策”“自动规划”“模型替代专家”等容易引发误解的表述。

UWM 的正确定位是增强城市治理能力，而不是替代城市治理责任。

## 13. 对公司管理层的战略意义

### 13.1 从 GIS 工具公司走向城市空间智能能力公司

如果公司只提供图层展示、空间查询和项目制数据处理，容易陷入传统 GIS 工具竞争。UWM 可以把公司能力从“展示城市”推进到“理解城市、推演城市、比较方案、审计证据”。

### 13.2 从城市驾驶舱竞争走向智能推演竞争

城市驾驶舱和数字孪生市场已经高度拥挤。UWM 的差异化不在大屏，而在可验证的状态构建、动作推演、方案比选和证据审计。这是更接近业务决策和治理闭环的能力。

### 13.3 从一次性项目交付走向可复用平台能力

UWM 的数据契约、renderer、simulator、planner、evidence gate 和 benchmark 可以形成可复用模块。一个城市试点沉淀下来的能力，可以迁移到其它城市、区县和业务主题。

### 13.4 从概念竞争走向真实验证竞争

世界模型、智能体和城市数字孪生都容易成为概念竞争。UWM 必须通过真实数据、真实 holdout、历史回放、政策 outcome 和业务复核建立壁垒。谁能把概念转化为可验证证据，谁才可能形成长期竞争力。

## 14. 结语

UWM 的价值不在于给城市贴一个“世界模型”标签，而在于把城市治理中的真实问题组织成可计算、可推演、可审计的状态-动作-证据体系。

城市宜居性不是一个简单分数。它涉及居民是否暴露在高温和污染中，是否能公平获得公共服务，是否能在合理成本内到达生活机会，是否处于安全、健康、便利和有尊严的城市环境中。一个真正有价值的 UWM，必须能够说明：

- 当前城市状态是什么；
- 哪些区域和人群处于风险中；
- 风险由什么机制造成；
- 可以采取哪些治理动作；
- 干预后可能怎样变化；
- 哪些结论有真实证据支持；
- 哪些结论仍然需要人工复核或补充数据。

当前 UWM 已经具备从数据基础到 renderer、simulator、planner 和评估门控的工程骨架，也已经在状态预测和 known-effect proxy 场景中形成初步验证。但要成为城市治理中的可信生产能力，还必须进入真实权威数据、真实业务流程和真实政策 outcome 验证。

因此，UWM 最适合的下一步不是做更华丽的演示，而是选择一个明确城市治理问题，以数据清单、状态构建、动作推演、证据门控和人工复核为主线，开展分级试点。这样既能控制风险，也能把 UWM 从技术概念推进为可落地、可复用、可验证的城市空间智能能力。

- UWM 仍需真实政策 outcome、站点校准环境观测、权威人口和出行数据以及因果门控，才能支撑更高等级政策效果声明。

- UWM 已经自动完成城市规划；
- UWM 可以替代规划师、管理部门或专家审查；
- UWM 已证明真实政策效果优于传统方法；
- proxy target 就是真实宜居性结果；
- 合成数据可以替代真实观测；
- 大模型问答结果可以直接作为城市治理依据。
