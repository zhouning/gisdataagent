目前已经形成可以在本机 Kubernetes 中运行的最小闭环：

```text
Web 页面/API
```

## 3. 当前开发访问方式

启动端口转发：

```bash
./scripts/k8s-hydro-workbench-dev.sh forward
```

访问：

```text
http://localhost:8091
```

常用运维命令：

```bash
./scripts/k8s-hydro-workbench-dev.sh build
./scripts/k8s-hydro-workbench-dev.sh deploy
./scripts/k8s-hydro-workbench-dev.sh status
```

部署只使用 `gis-agent-hydro-dev`，不会覆盖已有 `gis-agent` 命名空间。

Docker Desktop 使用 ARM64 水动力运行时。正式 H100 节点应构建同一工作台镜像的
AMD64 版本，例如将 `HYDRO_RUNTIME_IMAGE` 设置为客户环境验证过的 Linux AMD64
运行时，并在镜像仓库中以不可变 digest 发布；不能把本机 ARM64 镜像直接当作 H100
节点镜像。

## 4. 当前数据边界

客户原始 GDB、0.5 m DTM、泵站、潮位和管网监测数据目前不能直接提交给模型。系统当前对 `customer_mount` 执行采取 fail-closed 策略：即使 URI 已填写，在 GDB/DTM ETL 适配器完成之前，也不会静默改用开发夹具计算。

下一步客户数据链应为：

```text
NAS/对象存储原始数据
→ 数据资产登记和版本选择
→ AOI 窗口读取
→ GDB 字段映射、拓扑修复和单位统一
→ DTM COG/窗口裁剪、清洗和重采样
→ 生成模型可用 SWMM INP 与 ANUGA 网格
→ 数据预检
→ 才允许创建模型 Job
```

这是当前最重要的未完成项，也是从“运行演示”进入“客户数据可用”的关键路径。

## 6. 下一批开发任务

1. 建立客户数据资产目录，接入对象存储/NAS URI、版本和权限；

5. 把独立工作台前端正式接入 GIS Data Agent 新 Tab；
6. 将结果发布为适合 Web 的时序、COG/MVT/PMTiles，并增加时间滑块；
7. 在客户 K8s 上确认 CSI、对象存储、Ingress、CPU/内存/临时盘和 GPU Operator；
8. 用一个真实小区域和经过 ETL 的客户数据做第一轮端到端验收。

## 7. 关键结论

当前已经证明“网页/API → Manifest → K8s Job → 一维/二维/耦合求解器 → 持久化结果 → Web 查询”的执行链可行。下一阶段不应继续扩大开发夹具，而应优先完成客户 GDB 和 DTM 的区域 ETL，以及正式 GIS Data Agent Tab 的接入。
