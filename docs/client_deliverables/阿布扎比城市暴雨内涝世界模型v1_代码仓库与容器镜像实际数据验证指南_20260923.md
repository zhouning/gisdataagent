## 1. 文档目的

本文档说明其他团队如何基于 GitHub 代码仓库、已交付的 Docker 镜像和经授权的阿布扎比客户数据，走通阿布扎比城市暴雨内涝世界模型 v1 的实际数据验证流程。

文档同时区分三类结果：

1. **容器运行时验证**：确认 SWMM、ANUGA、耦合适配器和可选 LISFLOOD-FP 能够在目标架构上启动并产生规定制品。
2. **客户真实数据验证**：将客户全市 SWMM、二维地形网格和接口映射挂载到容器中，检查输入、执行计算并审核输出质量门。
3. **Web 应用集成验证**：确认页面和 API 如何加载已有结果、调用 GWM；当前代码中的 Web 阶段 2/3 尚未自动调度水动力容器，不能把命令行容器验收等同于 Web 页面已经容器化。

文档不把未通过项目包装为通过。当前实测中，阶段 2 全市 SWMM 在默认 2700 秒内未完成，阶段 3 真实双向耦合的交换量质量门未通过；这两个限制在后文单独列出。

## 8. 阶段 3：二维水动力与耦合验证

阶段 3 使用核心镜像中的 ANUGA 和耦合运行器。客户真实运行建议先执行 600 秒短验证，再决定是否提交完整城市时长。直接运行器消费已准备好的场景 INP；Web 阶段 3 API 会在提交任务时创建 run-local 的 coupled_scenario.inp。

### 8.1 真实单向耦合

~~~bash
docker run --rm \
  --pull never \
  --platform "$PLATFORM" \
  --network none \
  --read-only \
  --tmpfs /tmp:size=512m,mode=1777 \
  --mount type=bind,src="$ABU_DHABI_HYDRO_INPUT_DIR",dst=/data/input,readonly \
  --mount type=bind,src="$ABU_DHABI_HYDRO_RUN_DIR",dst=/data/runs \
  --entrypoint python \
  "$CORE_IMAGE" \
  /app/scripts/run_abu_dhabi_swmm_anuga_bidirectional_pilot.py \
  --swmm-inp /data/input/swmm/abu_dhabi_city_full_topology.inp \
  --swmm-library /opt/swmm/lib/libswmm5.so \
  --grid /data/input/surface/terrain_grid_250m.npz \
  --bindings /data/input/coupling/interface_bindings.jsonl.gz \
  --output /data/runs/stage3-real-one-way-600s \
  --duration-seconds 600 \
  --window-seconds 300 \
  --coupling-mode one_way_swmm_to_anuga \
  --binding-limit 1000 \
  --interface-detail-limit 1000 \
  --run-id container-real-one-way-600s \
  --quiet
~~~

预期输出：

~~~text
bidirectional_coupling_receipt.json
delivery_summary.json
maximum_depth_wgs84.geojson
temporal_snapshots/manifest.json
abu_dhabi_swmm_anuga_bidirectional_pilot.sww

~~~

本次 ARM64 和 AMD64 均完成，两个 300 秒交换窗口均有记录，quality_passed=true。结果属于诊断性 coupled run，不能自动解释为工程准入结果。

### 8.2 真实双向耦合

将上面命令的输出目录、耦合模式和 run ID 替换为：

~~~bash
  --output /data/runs/stage3-real-two-way-600s \
  --coupling-mode two_way_swmm_anuga \
  --run-id container-real-two-way-600s
~~~

本次 ARM64 和 AMD64 均能完成计算，但质量门失败：

~~~text
quality_passed=false
第一个窗口：通过
第二个窗口：失败
总质量残差：约 -6.95e-11 m³（接近零）
请求有符号交换量：95,696.097 m³
实际施加有符号交换量：108,743.571 m³
差值：13,047.474 m³
相对偏差：0.1199838654（约 12%）
~~~

初步定位为多个 SWMM 接口绑定到同一 ANUGA cell；当前 _bounded_head_rate() 对每个接口分别使用同一 cell 的可用水量，接口汇总后可能超过该 cell 可排出的实际水量，随后被 ANUGA 截断。当前质量门比较“请求量”和“施加量”，因此失败。问题与 ARM64/AMD64 架构无关。

在该缺陷修复并重新生成接口映射、复跑双向质量门前，不得将阶段 3 双向标记为完整通过，也不得把本次输出用于工程设计责任结论。

## 11. 当前 Web 容器化边界

当前实现必须按以下方式理解：

~~~text
页面 → Web API → 本机 subprocess / 本机 Python、SWMM 进程
~~~

当前尚未实现：

~~~text
页面 → Web API → Docker 水动力容器调度器
~~~

deploy/abu-dhabi-hydrodynamics/compose.yml 是独立 runtime 的运行入口，不是 Web API 的自动调度器。若要让页面点击阶段 2/3 后直接在容器内执行，需要另行实现：

1. Web API 的容器 job adapter；
2. 输入数据和 /data/runs 的安全挂载策略；
3. Docker socket、容器编排平台或受控 worker 队列；
4. 任务状态、取消、超时、日志和审计回传；
5. 运行结果注册到现有阶段 3/5 读取合同；
6. 对双向耦合质量门失败的显式 UI 状态。

在该集成完成前，交付验收应使用本文档中的命令行容器流程；页面验证只验证预计算结果加载和阶段 4 GWM 实时推理。

## 12. 端到端验收顺序

建议严格按以下顺序执行：

1. 固定 Git 分支和提交，记录 git rev-parse HEAD。
2. 校验离线镜像 tar 的 SHA-256，再加载与主机匹配的架构。
3. 运行 load-and-smoke.sh，确认运行时基础能力。
4. 准备客户数据目录和 manifest.json，只读挂载输入目录。
5. 执行阶段 1 --check --require-customer-data。
6. 执行阶段 2 全市 SWMM；默认 2700 秒只作为短时诊断，正式复测使用 7200 秒或更长。
7. 执行阶段 3 单向 600 秒短验证并检查全部输出制品。
8. 执行阶段 3 双向 600 秒短验证；如 quality_passed=false，保留证据并停止“完整通过”结论。
9. 加载冻结 GWM 容器，执行健康、就绪、模型和实时推理检查；不执行训练。
10. 将阶段 2/3 已有结果目录挂载到 Web 应用配置路径，检查阶段 5 API、地图和时间片加载。
11. 单独检查 506 个客户积水热点图层，不与模拟结果混淆。
12. 保存所有命令、镜像 ID、数据 SHA-256、运行 receipt 和质量门结果，形成验收包。

## 13. 排障手册

### 13.1 customer_data.status=failed

检查：

~~~bash
shasum -a 256 /srv/abu-dhabi-hydro/input/swmm/abu_dhabi_city_full_topology.inp
stat -f '%z bytes' /srv/abu-dhabi-hydro/input/swmm/abu_dhabi_city_full_topology.inp
~~~

处理：恢复正确版本文件，重新生成 manifest；不要修改 manifest 去“迎合”错误文件。

### 13.2 exec format error

原因通常是镜像架构与 Docker 运行平台不一致。检查：

~~~bash
docker image inspect "$CORE_IMAGE" --format '{{.Os}}/{{.Architecture}}'
uname -m
~~~

优先加载匹配架构 tar；只有在明确批准的仿真环境下才使用 --platform 跨架构运行。

### 13.3 阶段 2 超时

确认输出目录仍有增长，检查宿主机 CPU、内存、磁盘和容器日志。将 --timeout-seconds 提高到 7200 或更长；不要把部分 .out 当作完成结果。

### 13.4 阶段 3 双向质量门失败

同时保存：

~~~text
bidirectional_coupling_receipt.json
delivery_summary.json
maximum_depth_wgs84.geojson
temporal_snapshots/manifest.json
~~~

重点分析相同 anuga_cell_index 的接口聚合、请求交换量、实际施加交换量和可用水量。当前问题是绑定粒度和 cell 级容量截断的合同不一致，不是 CPU 架构问题。

### 13.5 GWM ready 失败

检查模型目录是否只读挂载、模型卡和 run_receipt.json 是否完整、镜像是否为 GWM-R1-20260914 对应版本。不要在生产容器内临时训练来绕过 readiness。

### 13.6 页面显示“已有结果”但地图为空

检查 manifest.json 中时间片路径是否为相对路径，第一帧是否允许为空，maximum_depth_wgs84.geojson 是否为合法 FeatureCollection，以及 Web 应用环境变量是否指向客户结果根目录而不是容器内不存在的本机路径。
